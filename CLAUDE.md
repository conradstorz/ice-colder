# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**ice-colder** is a vending machine controller (VMC) application. It manages product selection, payment processing, hardware communication (MDB bus), and provides a web-based dashboard for monitoring and configuration.

## Layout

The repo is a uv workspace (`packages/*`). **Migration in progress:** `ice_contracts`, `ice_common`, `ice_ui`, `ice_edge` and `ice_sims` are populated (the former `controller/`, `services/`, `config/` and `web_interface/` roots are gone; `main.py` is `ice_edge/__main__.py`); the former `simulators/` root is now `ice_sims`. ### Package dependency rules (enforced by `uv run lint-imports` and `scripts/check_package_isolation.py`)


- Lowest to highest: `ice_contracts` → `ice_common` → `ice_ui` → (`ice_edge` | `ice_cloud` | `ice_sims`).
- A package imports only packages below it.
- The three top packages are mutually independent.
- `ice_sims` additionally may not import `ice_ui`, because boards have no UI.
- `ice_ui` may import only `ice_contracts`, never `ice_common`.

Rebuild and commit `app.css` by hand whenever templates change; a stale file (leftover classes from a deleted template, or a missing rebuild after one) passes CI silently and only a manual rebuild catches it.

## Architecture

### Entry Point & Startup (`packages/edge/src/ice_edge/__main__.py`)

`main()` loads `config.json` into a Pydantic `ConfigModel`, then runs four
concurrent asyncio tasks on a single event loop: a uvicorn web server (host/port
from `config.web`, default `0.0.0.0:26123`, with sessions persisted in
`data/access.json`), the MQTT client, the health monitor, and the report
scheduler. `packages/common/src/ice_common/task_supervisor.py` provides the reusable
`supervise(name, coro_factory, restart_delay=5.0)` helper: background components
restart after a crash or unexpected return, but cancellation propagates.
`packages/common/src/ice_common/task_lifecycle.py` provides `run_until_primary_exits(primary,
*background)`: when uvicorn finishes or fails, background tasks are cancelled
and awaited before application cleanup (Docker's `restart: unless-stopped`
handles process-level restarts). Neither helper imports application components.

### Configuration (`packages/common/src/ice_common/config_model.py`, `config.json`)

All configuration is a single Pydantic `ConfigModel` loaded from `config.json`. The model has eight top-level sections: `version`, `physical` (machine details, people, products), `payment` (Stripe, PayPal, MDB), `communication` (email, SMS, Snapchat gateways), `mqtt` (broker connection), `web` (dashboard host/port/trusted proxies), and `reports` (scheduled sales-summary email: `schedule` off/daily/weekly, `hour` 0–23, `weekday` Monday-based 0–6, `extra_recipients`), and `cloud` (optional uplink: `enabled` default **false**, `url` default `http://127.0.0.1:26124`, `report_interval_seconds` 10–3600, default 60) — plus the scalar `machine_id` field. The reports section is edited at **`/settings/reports`** gated on `edit_contacts`. `ConfigModel` exposes convenience properties (e.g., `config.products`, `config.machine_owner`, `config.stripe`) so consumers don't need to navigate the nested structure. Missing keys are filled from Pydantic defaults at load time. Saves via
`packages/edge/src/ice_edge/config/config_store.py` are atomic (tmp + rename), write real secret values,
and keep a rolling `config.json.bak`.

`packages/edge/src/ice_edge/app/startup_config.py` owns config loading, first-run creation,
environment overrides, and the startup access-store / setup-mode warning
(`warn_if_setup_mode`); `__main__.py` calls it during startup. The config file path
is configurable via the `ICE_COLDER_CONFIG` environment variable (read at call
time by both `packages/edge/src/ice_edge/app/startup_config.py` and `packages/edge/src/ice_edge/config/config_store.py`),
defaulting to `config.json` in the current working directory when unset. This
lets Docker point the app at a writable, bind-mounted location instead of
relying on a bind-mount targeting `config.json` directly (which would let
Docker create it as a directory on a fresh clone, since the file is
gitignored). If the resolved config path exists but is a directory, startup
logs a clear error and exits with code 1 rather than papering over it.

### Cloud uplink (`ice_edge/uplink/`)

Off unless `config.cloud.enabled`. `ice_edge/__main__.py` then adds a supervised `uplink` task running `run_uplink`: it `PUT`s the `ice_ui` bundle once (retried each interval until accepted), then forever `POST`s a `MachineReport` (built by `build_machine_report` from the `ice_edge.views.health` builders; a pure read) to `{url}/api/v1/machines/{machine_id}/report`, re-reading `report_interval_seconds` each pass. `HttpUplink` has a 5 s timeout and never raises (failure logs a warning and returns `False`); there is no outbox, each report supersedes the last, and a sale is never blocked. `ice_edge.uplink` sits above `views` and below `app`/`web`, so it imports `Machine` only under `TYPE_CHECKING`.

### Dispenser profiles (`dispensers.toml`)

A standalone, hand-edited `dispensers.toml` gives each physical dispense slot (`[slot.N]`) its own mechanism parameters (agitate/fill/release timings, channel names, accessory lead/lag) — separate from `config.json`'s product catalog, which only knows a product's `sku`/`slot`/`kind`. The file lives next to `config.json` and is resolved the same way: the `ICE_COLDER_DISPENSERS` environment variable (read at call time, mirroring `_config_path`), defaulting to `dispensers.toml` in the current working directory. Like `config.json`, it is gitignored (`.gitignore`), so a fresh checkout has none; `dispensers.example.toml` is the committed, generated reference a first run copies from. Only the `vmc` compose service sets `ICE_COLDER_DISPENSERS=/app/data/dispensers.toml` — the VMC is the only reader: it sends a product's whole validated `SlotProfile` inside the `DispenseCommand` it dispatches, so the simulators never read the file themselves and their copy of the env var (present through plan 1) was removed once plan 2 shipped the runtime wiring below.

Three modules split the work. `packages/contracts/src/ice_contracts/board/dispenser_schema.py` holds the Pydantic models for one slot's profile (`SlotProfile`, a discriminated union of `BaggedIceProfile`/`WaterFillProfile`) plus the per-mechanism step models (agitate/fill/release, accessories) and helpers (`drive_channels`, `sense_channels`, `worst_case_seconds`, `MECHANISM_FOR_KIND`). `packages/edge/src/ice_edge/vend/dispensers.py` owns validation and file I/O: `validate_document(text, products, capabilities=None, dispense_timeout_seconds=120.0)` runs TOML parsing, per-slot schema validation, and cross-checks (catalog sku/slot/kind agreement, channel drive/sense conflicts, the dispense time budget, and — when a vending board's capabilities are known — channel direction) into a `ValidationReport` (`.findings`/`.errors`/`.warnings`/`.ok`/`.file_error`/`.render_text()`, each a list of `Finding(slot, path, line, severity, message)`); `DispenserProfiles(config, path=None)` wraps that with `.load()`, `.validate_text()`, `.save_text()` (atomic, digest-guarded), `.profile_for_slot()`, and `.set_capabilities()`. `packages/edge/src/ice_edge/vend/dispensers_doc.py` generates `dispensers.example.toml` from the schema's own field metadata (descriptions, units, ranges, discriminator tags) so the example cannot drift from the schema it documents; regenerate it with `uv run python scripts/gen_dispensers_example.py` after any schema or sample-value change, and `tests/edge/vend/test_dispensers_example.py` fails CI on byte drift. `uv run python -m ice_edge.vend.dispensers --check` validates the active file against the live catalog and prints a human-readable report (exit 1 on any error); `--example` prints the generated reference instead.

`CFG-101` (no valid dispenser profile for a slot, product-scope, `product_unavailable`) and `CFG-102` (`dispensers.toml` could not be read, machine-scope, `warning`) are registered in `packages/contracts/src/ice_contracts/board/vending_machine.py` (contract version 0.8.0). The file is loaded and its `ValidationReport` logged at startup (`ice_edge.app.startup_dispensers.load_dispenser_profiles`, called from `main()` right after `load_config()`; each finding logs at `warning` or `error` per its own severity, the verdict line at `info`; a directory at the resolved path logs a clear error and `sys.exit(1)`, mirroring `load_config`'s own check). The loaded `DispenserProfiles` instance is then handed to both the VMC and the routes module by `ice_edge.app.startup_dispensers.wire_dispenser_profiles(machine, profiles)`, called right after `machine.set_health_monitor(health)`. `Machine.set_dispenser_profiles(profiles)` stores it and immediately calls `reconcile_dispenser_profiles()`, which re-derives every product's `CFG-101` lockout and the machine's `CFG-102` fault from the currently loaded profiles — raising `CFG-101` for a sku with no valid profile, clearing it only when the existing lockout is `CFG-101` itself, and never touching another code's lockout. `machine.gate.profile_for(product)` is the single read path `machine.gate.reconcile()`, `DispenseCycle.start`, and `TestSaleRunner.run_test_sale` go through; `select_product` itself never calls it — it refuses a locked sku the same way it refuses any other lockout, by checking `self._faults.lockouts.get(candidate.sku)`, which `machine.gate.reconcile()` populated with `CFG-101` for that sku.

This gating lives in `packages/edge/src/ice_edge/vend/dispenser_gate.py`'s `DispenserProfileGate` — it owns the loaded `DispenserProfiles` object and `profile_for`/`reconcile`/`catalog_changed`/`on_vending_capabilities`; `Machine.set_dispenser_profiles` is a one-line delegate onto `attach`, and `gate` is the public read-only `@property` over the `DispenserProfileGate` itself on `Machine` — tests and routes read `machine.gate.profiles`/`machine.gate.profile_for(...)`/`machine.gate.reconcile()`/`machine.gate.catalog_changed()` directly. `FaultService.clear_fault`'s CFG-101 re-check goes through `self._lacks_valid_profile(sku)` (a callable `Machine` wires to `self._gate.lacks_valid_profile`) rather than reaching into the gate's internals itself.

Three deliberate deviations from the original design doc, recorded here rather than silently drifting: there is no top-level `DispenserFile` model, because each `[slot.N]` table is validated independently so one malformed slot only loses that slot, never the whole file; channel ids use the contract's own `CHANNEL_ID_PATTERN` (`packages/contracts/src/ice_contracts/board/common.py`) rather than a separate pattern; and the 0.7.0 → 0.8.0 contract bump that added `CFG-101`/`CFG-102` was originally this feature's only version bump — the VMC/routes runtime wiring (`DispenseCommand`, `DispenseStep`, the new `DispenserOutcome` members, `fault_for_outcome`) first reused that same 0.8.0 section on the theory that it was additive, not a schema break, but a Copilot review of PR #32 caught that `dispense`'s params actually changed shape and `cmd/dispense` was removed outright — wire-breaking, so `CONTRACT_VERSION` was bumped again, to **1.0.0**, per the module's own major-bump rule for breaking changes; see the Fault Codes section below for that bump's detail. Further deviations recorded for that runtime increment: `DispenserStatus.state` stays typed `str` rather than becoming an enum (both `DispenseStep` and `DispenserOutcome` strings flow through the same field over the sale's lifetime); the simulator's legacy `cmd/dispense` subscription was removed immediately rather than kept alongside the new path for a deprecation window, since no physical board exists yet to break; the command dispatcher reports a `door_open` completion as `status="failed"` (with a `detail` explaining the bag released but the door did not close) even though the VMC itself treats `door_open` as a customer success plus a fault, because the dispatcher's ack vocabulary has no third state; and `SessionSnapshot.dispense_mechanism` was added to the crash snapshot, additive beyond what the spec asked for.

### FSM Core (`packages/edge/src/ice_edge/sale/vmc.py`, `packages/edge/src/ice_edge/app/machine.py`)

`VMC` is the sale finite-state machine, seven explicit trigger methods over one `_transition(source, dest, before)` helper, and nothing else. States: `idle` -> `interacting_with_user` -> `dispensing` -> back to `idle` (or `error` from any state). Extra transitions: `cancel_sale` (interacting → idle, catalog edit removed the selection) and `vend_failed` (dispensing → interacting, price restored to escrow, product locked out per `packages/contracts/src/ice_contracts/board/vending_machine.py`'s `FAULT_TABLE`). The seven triggers (`start_interaction`, `dispense_product`, `complete_transaction`, `cancel_sale`, `vend_failed`, `error_occurred`, `reset_state`) each name their source state, destination and `before` hook in one `_transition` call; an invalid trigger raises `InvalidTransition`; `set_state(state)` forces a state with no hook or observer (the two in-FSM bypasses in `_fail_vend`/`_expire_session`, and the test seam). The other public methods -- `deposit_funds`, `select_product`, `process_payment`, `request_refund`, the session timer (`packages/edge/src/ice_edge/sale/session_timer.py`'s `SessionTimer`, armed and cancelled by the FSM; `_expire_session` is the expiry policy), `_fail_vend`, `_finish_dispensing`, `snapshot()`, and `sale` are the whole of the class. Refunds are real: `request_refund` publishes `cmd/payment/refund` and tracks the ack. Heartbeat loss (raised by `FaultService.on_subsystem_liveness`, not the VMC) maps to `COM-101` (vending), `COM-102` (ice maker), `PAY-101` (MDB); a broker disconnect maps to `COM-103` (`FaultService.on_mqtt_connection`); both auto-clear on recovery.

**The dependency rule.** `VMC` holds no transport or service handle — no MQTT client, health monitor, session store, event recorder, command dispatcher, display controller, or maintenance-lease reference. Its `__init__` takes `config` plus eleven required keyword-only collaborators: `tasks` (`TaskRunner`), `escrow` (`EscrowLedger`), `refunds` (`RefundProtocol`), `faults` (`FaultService`), `outputs` (`StatusOutputs`), `journal` (`SaleJournal`), `gate` (`DispenserProfileGate`), `dispense_factory` (builds one `DispenseCycle` per sale), and three read-only callables -- `in_maintenance() -> bool`, `availability() -> Availability | None`, `inventory() -> InventoryManager | None`. Everything the FSM publishes, persists, displays, or messages to the customer goes through `outputs`; every fault it raises or clears goes through `faults`. `packages/edge/src/ice_edge/app/machine.py`'s `Machine` is the sole construction path and builds every one of these before building the VMC itself. Import-linter enforces the layer order of `ice_edge` (contract 4: `app > web > uplink > views > sale > ...`, runtime imports only, so nothing outside `app/` can import `ice_edge.app`) and, as contract 5, that `packages/edge/src/ice_edge/sale/vmc.py` directly imports none of `ice_edge.app`, `ice_edge.sale.maintenance_lease`, `ice_edge.sale.test_sale`, `ice_common.mqtt_client`, `ice_edge.monitoring.health_monitor`, `ice_edge.ledger.session_store` -- except the plain `SessionSnapshot` value object `snapshot()` constructs, the one permitted ignore --, `ice_edge.ledger.event_recorder`, `ice_edge.hal.command_dispatcher`, or `ice_edge.customer_ui.display_controller` (indirect chains such as `vmc -> dispense_cycle -> command_dispatcher` are allowed). `tests/meta/test_no_private_access.py` carries the separate per-file private-access budget ratchet (below).

**`Machine` (`packages/edge/src/ice_edge/app/machine.py`).** The composition root `ice_edge/__main__.py` builds once. `Machine(config, *, tasks=None)` constructs, in dependency order, `TaskRunner`, `EscrowLedger`, `FaultRegistry`, `StatusOutputs`, then `FaultService`, `RefundProtocol`, `DispenserProfileGate`, `MaintenanceLease`, `SessionRecovery`, `TelemetryRouter`, the `DispenseCycle` factory, `VMC`, and finally `TestSaleRunner` (built last, since it alone holds a direct reference to the already-built VMC). Where two collaborators need each other before both exist -- the lease needs `vmc.make_idle_for_service`, the VMC needs `lease.hold` -- `Machine` passes a closure over its own attribute (`lambda *a: self.vmc.<method>(*a)`), resolved only when actually called, long after construction finishes, so the apparent circularity never bites. `Machine` owns ten `set_*` service attachments (`set_mqtt_client`, `set_health_monitor`, `set_availability`, `set_display_controller`, `set_inventory_manager`, `set_event_recorder`, `set_session_store`, `set_command_dispatcher`, `set_dispenser_profiles`, `set_session_liveness`), `attach_to_loop`, `cancel_pending_tasks`, `drain_persistence`, and twenty-one read-only properties (`vmc`, `tasks`, `escrow`, `faults`, `outputs`, `refunds`, `gate`, `lease`, `test_sales`, `recovery`, `telemetry`, `session_store`, `mqtt_client`, `command_dispatcher`, `health_monitor`, `availability`, `event_recorder`, `display_controller`, `inventory`, `maintenance_hold`, `subsystem_capabilities`). `set_session_store` runs the boot-time snapshot evaluation (`SessionRecovery.evaluate_at_boot()`, logging the `discard_test` warning or calling `Machine._flag_uncertain_session` on `uncertain`) and backs the four PAY-104 recovery forwards (`pending_sale_for_recovery`, `pending_sale_already_recorded`, `reserve_pending_sale`, `mark_pending_sale_recorded`) that routes and 20+ tests call as `machine.<method>()`. `packages/edge/src/ice_edge/web/context.py` stores `machine_instance` and sets `vmc_instance = machine.vmc` in lockstep, so the many pre-existing `context.vmc_instance` reads keep working. `SUBSCRIPTIONS` (`packages/edge/src/ice_edge/hal/mqtt_inbound.py`) is `(topic, owner, method)` triples -- `owner` is `"vmc"` for the four sale-driving handlers or `"telemetry"` for the other nine -- that `Machine.set_mqtt_client` resolves against `self.vmc`/`self.telemetry`, in table order.

**Public surface:** tests and routes reach the VMC only through its public surface, never an underscore attribute. Read-only: `faults` (the `FaultService`), `escrow` (`EscrowLedger`), `refunds` (`RefundProtocol`), `outputs` (`StatusOutputs`), `sale` (a `SaleContext`, `packages/edge/src/ice_edge/sale/sale_context.py`, `None` when no sale is in flight; `selected_product` is a read/write property and `pending_sale_shares` a read-only property, both over `sale`), `credit_escrow`/`escrow_credits` (read/write conveniences over `escrow`), `test_sale_in_progress`, `state` (a plain attribute; mutate only through a trigger or `set_state`), `products`, and the public instance attributes `session_timeout_seconds`/`dispense_timeout_seconds`. The event port: the four sale-driving inbound handlers (`on_payment_credit`, `on_button_press`, `on_dispenser_event`, `on_refund_ack`), the two callbacks a `DispenseCycle` invokes (`on_dispense_failed`, `note_dispense_request`), `process_payment()`, and `raise_fault`/`clear_fault` (one-line forwards onto `FaultService`, kept because the FSM is a legitimate raiser). The test-sale seams: `begin_test_sale(product) -> bool`/`end_test_sale()`/`find_product(sku)`, and `make_idle_for_service()` -- the one FSM operation `MaintenanceLease.begin_standby` cannot do for itself. The observer hooks `TestSaleRunner` uses: `subscribe_state_change`/`subscribe_sale_settled`. `snapshot()`, `cancel_timers()`, `get_status()`, and `active_faults()` round it out. Everything else -- the ten `set_*` service attachments, `attach_to_loop`, `cancel_pending_tasks`, `drain_persistence`, the service properties (`session_store`, `mqtt_client`, `command_dispatcher`, `health_monitor`, `availability`, `event_recorder`, `display_controller`, `subsystem_capabilities`), `recovery`, `telemetry`, `lease`, `gate`, `tasks`, `test_sales`, `maintenance_hold`, the four PAY-104 recovery forwards, the QR-cycling body of `initiate_virtual_payment` (moved to `PaymentGatewayManager.next_payment_prompt`), and `run_test_sale` itself -- lives on `Machine` or its collaborators, below. The rule is otherwise unchanged: tests and routes may **read** a collaborator directly (`vmc.faults.is_locked(sku)`, `vmc.sale.is_test`, `machine.gate.profiles`, `machine.lease.hold`, ...) but **mutate** only through a VMC/Machine method -- never by poking a collaborator or a `vmc._<name>`/`machine._<name>` attribute. Time is under the same discipline: `tests/fakes.py`'s `FakeTaskRunner` stands in for the real `TaskRunner`; the `machine`/`vmc` fixtures build a `Machine`/its `.vmc` with a real one, and `machine_fake_time`/`vmc_fake_time` build them on a `FakeTaskRunner` attached to the running loop instead, yielding `(machine, runner)`/`(vmc, runner)`; every timer the VMC or a collaborator arms carries one of six labels -- `dispense_timeout`, `session_timeout`, `process_payment`, `refund_deadline`, `maintenance_idle`, `standby_sweep` -- so a test fires it by label (`runner.fire("dispense_timeout")`) rather than reaching for the scheduled task itself. The same discipline extends to non-timer waits: `tests/fakes.py`'s `settle(turns=3)` yields to the loop a bounded number of times so a fire-and-forget task with no real I/O finishes, `FakeTaskRunner.drain_persistence()` awaits persistent tasks the same way the real `TaskRunner`'s does, and the simulator command loop's `queue.join()` (now that `command_loop` calls `queue.task_done()` in a `finally`) lets a test await every queued command's processing instead of sleeping past it. Tests never wait on the wall clock for synchronization -- the two sanctioned exceptions are a never-completing stand-in (`sleep(10|100|3600)`, meant to be cancelled or simply never reached before the test asserts) and a bounded poll interval checked in a loop. `asyncio.sleep(0)` remains common throughout (it yields one event-loop turn rather than waiting on the clock at all), and a documented, deliberate residual fixed sleep or two still survive where no public observable exists to poll instead (e.g. `tests/integration/test_integration_e2e.py`'s "Deliberate residual fixed sleep" comment).

`tests/meta/test_no_private_access.py` enforces the no-private-access rule across the whole suite as a per-file budget ratchet, not a hardcoded `vmc`/`machine` special case: `tests/private_access_budget.py`'s `BUDGET` dict caps how many private attribute accesses -- found by walking each file's `ast`: any `Attribute` node whose name is `_[a-z]...` on anything but bare `self`/`cls` (so `f()._x`, `xs[0]._x` and `(a or b)._x` count), plus `getattr`/`setattr`/`hasattr`/`delattr` calls whose second argument is a `"_x"` string; dunder access like `vmc.__class__` is excluded -- plus private `from m import _x` imports each `tests/**/*.py` file may have, and a file not listed has an implicit budget of 0. The test fails over budget, listing every offending `path:line`, and fails under budget too ("lower BUDGET[...] to N") -- budgets only ever move down, never up. **To lower one:** fix the tests until the count drops (promote the private name to a public seam, or stop reaching past one), run `uv run python tests/meta/test_no_private_access.py` to print the current counts, then edit that one number in `tests/private_access_budget.py`. A `# private: <reason>` marker (the reason must be non-empty; a bare `# private:` exempts nothing) on one of the three lines above a hit exempts that hit entirely (not the hit's own line -- the lookback window ends just before it) -- the escape hatch for a test that must reach a private to drive an otherwise-unreachable defensive branch. Because it parses code rather than matching text, a comment, docstring or string literal mentioning `obj._name` is never a hit (unlike `test_static_css.py`'s regex class extractor, Key Patterns below).

**`StatusOutputs` (`packages/edge/src/ice_edge/sale/outputs.py`):** the FSM's only outbound channel. Methods: `state_changed(state)` (push to health and availability, persist or clear the session via `persist`, publish a retained `status` message when an MQTT client and loop both exist); `persist(state=None)` (the PAY-104 evidence guard: a no-op while `pay104_active()`, so the crash evidence file is left untouched for the operator); `save_snapshot_async(snapshot)` (the awaited save `DispenseCycle.start` uses, same guard, for a caller that is already async rather than fire-and-forget); `clear_session_evidence()`; `display(state)`; `message(text)`/`refresh()` (the customer-message and dashboard-refresh callbacks); `show_qr(image)`; `publish_payment_enable(accept)`; `publish_refund(cmd)`; `publish_alert(alert)`. It owns the `update`/`message`/`qrcode` callbacks and the uptime clock; every sink (`mqtt`, `health`, `availability`, `session_store`, `display_controller`) is attached later via its own `attach_*` method and defaults to `None`, so the class is fully usable with nothing wired at all. `outputs` is the public read-only `@property` over it on the VMC. The QR-cycling body of `initiate_virtual_payment` lives in `PaymentGatewayManager.next_payment_prompt(amount) -> tuple[str, object] | None` (gateway name and QR image, cycling the index internally, `None` when no gateways are configured); the VMC's own `initiate_virtual_payment` just calls it, messages "unavailable" on `None`, else `outputs.show_qr` plus the "scan the QR code" message.

**`SaleJournal` (`packages/edge/src/ice_edge/sale/sale_journal.py`):** owns the `transaction=True`/`vending=True` bound loggers, the `vend_failed`/`error`/`refund`/`refund_failed` recorder rows, and the adjacent customer messages — one method per sale event. The VMC never calls `logger.bind` or `recorder.record` itself. The journal owns the sale's domain-event log lines (the bound sinks and their paired plain-logger lines), recorder rows and adjacent customer messages; incidental `logger.debug` tracing and the `MQTT dispenser event` line stay at the VMC call site. `Machine` builds it right after `StatusOutputs` and passes it to `VMC` as `journal=`. `tests/meta/test_vmc_complexity.py` is a size ratchet over `packages/edge/src/ice_edge/sale/vmc.py` (class code lines, file lines, largest method code lines) whose budgets only move down and which fails when more than 10% under budget.

**`FaultService` (`packages/edge/src/ice_edge/faults/fault_service.py`), wrapping `FaultRegistry` (`packages/edge/src/ice_edge/faults/fault_registry.py`):** the fault state itself -- `lockouts` (product-scope, by sku) and `machine_faults` (machine-scope, by code) -- lives in the pure `FaultRegistry`, the first piece carved off the VMC god object. `FaultService` layers every side effect on top: `raise_fault(code, *, sku=None, outcome=None)` and `clear_fault(key, by="admin")` run the event-recorder `lockout_set`/`lockout_cleared` rows, the `logger.error`/`logger.info` lines, the health-monitor alert raise/clear, the MQTT `alerts` publish, and the push of `active_faults()` to health and availability (`push_active_faults`), plus three guards -- `SVC-102` refused while the maintenance lease is held, `PAY-104` cleared only once the session evidence file is removed (then `set_transaction_certain(True)`), `CFG-101` re-raised after any lockout clear leaves a profile-less product unlocked. It also owns `on_subsystem_liveness(subsystem, alive)` (COM-101/COM-102/PAY-101 plus the availability liveness push and the MDB republish), `on_mqtt_connection(connected)` (COM-103 plus republish and status), and `clear_ice101_lockouts()` (the `TelemetryRouter`'s `on_bin_half_full` callback). Five collaborators are injected as call-time callables rather than objects, since the VMC attaches or replaces what they read after construction: `recorder`, `lease_holder`, `lacks_valid_profile` (the CFG-101 re-check, wired to `gate.lacks_valid_profile`), `set_transaction_certain`, `fsm_state`. Reads are re-exposed verbatim: `is_locked(sku)`, `has(code)`, `lockouts`, `machine_faults`, `active_faults()`, `parse_key(key)`. `VMC.raise_fault`/`clear_fault`/`active_faults` stay one-line forwards onto `self._faults`; `faults` is the public read-only `@property` over the `FaultService` itself on both `vmc` and `machine` -- tests and routes read `vmc.faults.lockouts`/`.is_locked(sku)`/`.has(code)` directly rather than a VMC-private alias, and mutate only through `raise_fault`/`clear_fault`.

**`DispenseCycle` (`packages/edge/src/ice_edge/vend/dispense_cycle.py`):** one instance is built, through the injected `dispense_factory`, for every entry into `dispensing`, and held as `self._cycle` until the sale leaves that state; its own *identity* is what `on_dispense_failed` uses to tell a late callback from a superseded attempt apart from the current one (`cycle is self._cycle` and `self.state == "dispensing"` must both hold). `start(snapshot_for)` looks up the slot's profile via `gate.profile_for` (keyed on the product's own stable `slot` field, never its list position), mints `request_id` synchronously -- before any task exists, so no hardware report can race it -- arms the `dispense_timeout` timer, and fires the actual dispatch (`_run`) as a fire-and-forget task: `_run` awaits persisting the dispensing snapshot through `outputs.save_snapshot_async` (the PAY-104 evidence guard), then dispatches `dispense` through the command dispatcher with that `request_id` and checks the ack status -- all *after* the timer is already armed, which is exactly why a slow or failing dispatch can race the timeout and why the cycle-identity guard above exists. Every failure on that path -- no valid profile (`CFG-101`, `"no_profile"`), the snapshot save raising, no dispatcher wired, `CommandTimeout`, any other exception, or a non-`"ok"` ack -- calls `on_failed(cycle, code, outcome)` with `PAY-102` and the matching outcome string (`snapshot_failed`/`no_ack`), rather than waiting out the 120 s timeout fallback; the timer itself calls `on_failed(cycle, FaultCode.PAY_102, "no_report")`. `classify(data) -> DispenseReport | None` runs the slot-mismatch check, the `request_id` mismatch check (a report with no id at all is still accepted, keyed on slot alone), decides `door_open` is a customer success only when `(mechanism, door_open)` has an `OUTCOME_FAULTS` entry (bagged ice; never water fill), and otherwise resolves through `fault_for_outcome`, falling back to that mechanism's `error` mapping on an unmapped `(mechanism, outcome)` pair (a board mis-reporting for its own mechanism) rather than raising `KeyError` into the MQTT handler; `None` means "not for this cycle, ignore" (an intermediate step, a slot or id mismatch), and the cycle logs why. `record() -> bool` is the durable sale write: the `dispense` KPI event, then the `sales` row itself, off the loop via `asyncio.to_thread`, both skipped when no recorder is attached; price is the sum of the sale's own consumed shares, never `product.price` (an operator can edit the price mid-dispense). The sale is inserted **synchronously on its own WAL connection** (`synchronous=NORMAL`) and **awaited before the FSM returns to idle**. A generic insert failure is already journaled as a fallback by `record_sale` itself, so it raises the alert-class `DATA-101` and still returns `True`; `SaleRecordingFailed` (the insert *and* its journal fallback both failed) calls `set_transaction_certain(False)`, raises `PAY-104`, and returns `False` -- the caller's sole signal to keep `sale.shares` set so the on-disk "dispensing" snapshot stays the sale's only record, for the operator's "Record as sale" recovery; a `True` return (no recorder, the plain success path, or the `DATA-101` path) is what lets the caller clear `sale.shares`. At startup the journal is replayed idempotently on `(ts, sku)`, each row in its own transaction, so a crash mid-replay cannot duplicate a row and one bad row cannot block the others; `packages/edge/src/ice_edge/app/startup_recovery.py` clears `DATA-101` only once the journal is actually drained (absent or empty), never on the replay function's integer return (which is `0` both for "nothing to do" and "fully drained, all duplicates or rejects"). A corrupt `events.db` is renamed aside to `events.db.corrupt-<timestamp>`, a fresh database is created, and `DATA-102` is raised so the machine keeps running. `cancel()` drops the timer; the VMC calls it on every exit from `dispensing` (`_finish_dispensing`, `on_vend_failed`, `on_reset`, `on_cancel_sale`, `on_error`, and the success path itself, before the `await record()` suspension). `CFG-101` is a standing invariant enforced at two points: `select_product` refuses a profile-less product up front via the ordinary lockout path -- the sku is already `CFG-101`-locked in `vmc.faults.lockouts` by `machine.gate.reconcile()`, so `DispenseCycle.start`'s own profile lookup should never fail -- and `start` still re-checks and fails the vend with `CFG-101` if the profile vanished between selection and dispense (a `dispensers.toml` reload racing the sale), a defensive fallback, not the primary guard. The vending simulator's `water_flow` telemetry channel stays cumulative gallons; the per-fill flow-meter pulse count is its own `fill_pulses` channel, published alongside `agitator_current`/`auger_current` on `telemetry/vending/<id>` -- none of which the VMC subscribes to yet. Constructor dependencies: `sale`, `dispatcher()`, `gate`, `outputs`, `faults`, `recorder()`, `set_transaction_certain`, `tasks`, `timeout_seconds()`, and the two VMC callbacks `on_failed`/`on_request_id`.

**Observers and `TestSaleRunner` (`packages/edge/src/ice_edge/sale/test_sale.py`):** `subscribe_state_change(cb) -> unsubscribe` and `subscribe_sale_settled(cb) -> unsubscribe` are two independent, synchronous subscriber lists on the VMC; `_after_state_change` calls `outputs.state_changed(self.state)` then every state-change observer, in subscription order, and a raising callback is logged and never stops the rest. Settled fires exactly once per sale, through `_settle`, which captures the sale before running the settling transition; the three sites are `on_dispenser_event`'s success and failure branches and `on_dispense_failed`. The fired tuple is `(sale, outcome, fault_code)` and outcome is one of `"dispensed"`, `"vend_failed"`, `"timeout"`; never fired on cancel/reset/error. `TestSaleRunner.run_test_sale(sku, *, user_id=None, user_name=None) -> TestSaleResult` (constructed with `vmc`, `lease`, `gate`, `recorder()`, `tasks`) talks to the VMC only through this public surface: an unknown sku raises `ValueError`; a product with no valid profile (only when `gate.profiles` is wired) raises `RuntimeError` before anything else is touched; the **double-submit guard** -- `vmc.test_sale_in_progress` -- is checked *before* `lease.test_run()` is ever entered, so a refused second call never refreshes the lease's idle clock; then `with lease.test_run():` subscribes both observers, calls `vmc.begin_test_sale(product)` (a `False` return raises the "could not select" `RuntimeError`), awaits the settlement future, appends the settled state if the path's last entry differs (the `_fail_vend` "no sellable products" branch bypasses `_after_state_change` via `vmc.set_state()` directly), records the `test_run` event row, and in `finally` unsubscribes both observers and calls `vmc.end_test_sale()` -- but only when `begin_test_sale` actually ran (the `began` flag), since one that raised its own "already in progress" guard seeded nothing for this call to clean up. `begin_test_sale` is exception-safe: anything it raises between setting the in-progress flag and returning takes the just-deposited "test" credit off escrow directly and clears the flag and the seeded `SaleContext` before propagating. A failed **test** vend always takes the credit `on_vend_failed` just restored straight off escrow (`escrow.take_all()`) inside `_fail_vend`, whether or not a runner is still awaiting it; `end_test_sale`'s own `take_all()` is a backstop, not the only path.

**A test sale is exempt from its own `SVC-102`, and only from that:** the same failing `no_critical_fault` safety row that withdraws `cmd/payment/enable` also fails `Availability.sale_available`/`product_sellable` for an ordinary sale, so an unmodified lease would refuse the very product it exists to let a tech dispense. `product_sellable`/`sale_available` (`packages/edge/src/ice_edge/faults/availability.py`) take an `ignore_faults: frozenset[str]` (default empty, so every existing caller — including a customer's `select_product` reached during a lease — is unaffected); when every currently active blocking code is in that set, `no_critical_fault` is treated as passing for this call only, while every other row, and every other blocking code, still fails and still blocks normally. `Availability.test_sale_sellable(product)` calls it with exactly `{SVC-102}`. `VMC.select_product` picks `test_sale_sellable` over `product_sellable` when `self.sale is not None and self.sale.is_test` — the exemption is keyed on the sale, never on the lease, so a customer press reaching `select_product` during the same lease still finds `sale.is_test` false (or no sale at all), still calls `product_sellable`, and is still refused like any other safety-blocked sale. Any *other* active safety fault — a leak, a stuck trap door, a bad 24 V supply, a tripped heater high-limit — still fails `no_critical_fault` for a test sale exactly as it would a real one; running an actuator into a real hazard "because it's only a test" would be worse than the bug this fixed. `payment_enabled`/`payment_blocking_reasons` never consult `ignore_faults` — they read the rows directly — so `cmd/payment/enable` stays withdrawn for the entire lease regardless of which sale is attempted.

**Test-ness lives on the sale, not the hold:** `sale.is_test` is set only by `begin_test_sale` (called from `TestSaleRunner.run_test_sale`), on the `SaleContext` it seeds, and is read (never inferred from the maintenance lease) by the dispense-completion and timeout handlers to decide whether to call `DispenseCycle.record()` (skipped entirely for a test) or record a `test_run` event instead — so a test sale writes neither a `sale` nor a `dispense` row, and releasing the lease mid-run cannot reclassify it, because nothing about the recording path consults the lease. `SessionSnapshot.is_test` carries the same flag into the on-disk crash snapshot, set from `self._sale.is_test` (or, with no sale in flight, the `_test_sale_in_progress` re-entrancy guard) at the moment the snapshot is built. This is the money-safety consequence a review caught: without it, a test sale that crashed mid-dispense would leave an open snapshot that looks exactly like a real uncertain sale, and the `PAY-104` recovery flow would let an operator "Record as sale" it into the never-pruned `sales` table. `is_test` is checked at two chokepoints so that can never happen — `SessionRecovery.evaluate_at_boot()` discards a test-flagged snapshot found at boot instead of raising `PAY-104` for it at all, and `SessionRecovery.pending_sale_for_recovery()` refuses to surface one as a recoverable card even if some future path left `PAY-104` active anyway, as defence in depth. A future contributor adding a second persistence path for pending sales must carry `is_test` through it too, or this guarantee breaks silently.

**Maintenance lease (`MaintenanceHold`, `packages/edge/src/ice_edge/sale/maintenance_lease.py`'s `MaintenanceLease`, system-tests design §2.2/§2.2a):** the lease lifecycle -- the hold itself, its idle timer, the standby session-liveness sweep, and the grant/release/takeover/run accounting -- plus every FSM precondition it needs now live entirely on `MaintenanceLease`: `begin_maintenance(user_id, session_id)`, `begin_standby(user_id, session_id)`, `end_maintenance(session_id)`, and `take_over_maintenance(user_id, session_id)` all live there, taking `fsm_state() -> str`, `escrow_is_empty() -> bool`, and `make_idle_for_service() -> bool` as injected callables rather than holding a VMC reference. `begin_maintenance` grants a lease to take the machine out of service for operator testing -- refused unless the FSM is `idle`, escrow is zero, and no lease is already held; granting it raises `SVC-102` (via the lease's `on_granted` callback, which runs the VMC's `raise_fault`), which `packages/edge/src/ice_edge/faults/availability.py` treats as a **safety** row (built generically off `PAYMENT_BLOCKING_FAULTS`, not a special case), so `cmd/payment/enable` is withdrawn machine-wide for the whole lease. `begin_standby` -- a lease taken explicitly by a tech to make a *busy* machine idle and hold it out of service for the whole login session (`MaintenanceHold.standby`) -- calls `make_idle_for_service()` first (refunds any credit with `reason="maintenance"`, cancels a live customer sale) rather than requiring the machine to already be idle; refused only while `dispensing` ("vend finishing, tap again") or when a different session holds the lease ("held by <id>"), and upgrades the caller's own opportunistic lease to standby in place rather than replacing it. `MaintenanceHold` is a dataclass with `runs_in_flight` (an in-progress-run counter, not a boolean) plus `release_requested`/`release_reason`: `end_maintenance` and the 5-minute idle timer (`idle_expired`) only defer a release while `runs_in_flight > 0`, and `test_run()` (a context manager `TestSaleRunner.run_test_sale` uses) increments on entry and decrements in a `finally`, so a failing or timed-out run still frees the lease. Unlike the opportunistic lease, a standby lease has no idle-timer release (`idle_expired` skips it once `hold.standby` and a liveness predicate is wired); instead a 30 s sweep (`arm_sweep`/`sweep_tick`) calls the predicate wired via `Machine.set_session_liveness(predicate)` -- `AccessStore.session_is_live`, applying the same idle-limit and absolute-cap rules as `resolve_session` but never refreshing `last_active_at` -- to check the holder's web session **without resetting its idle clock**; with no predicate wired (tests), a standby lease falls back to the ordinary idle timer. The lease is **never persisted** -- it lives only on the live `MaintenanceLease` instance (held by `Machine`) and is not part of `SessionSnapshot`, so a restart clears it. Credit arriving during a lease is **refunded, not escrowed**: `deposit_funds` reads the injected `in_maintenance()` callable and, unless the deposit's `payment_method == "test"` (the one credit `begin_test_sale` itself deposits), adds it to escrow only long enough to call `request_refund(reason="maintenance")` immediately. The three timing knobs (`MAINTENANCE_IDLE_TIMEOUT_SECONDS`, `MAINTENANCE_TAKEOVER_IDLE_SECONDS`, `STANDBY_SWEEP_SECONDS`) are `MaintenanceLease` class attributes read through injected callables, so tests shrink them per instance via `machine.lease.MAINTENANCE_IDLE_TIMEOUT_SECONDS = ...` rather than waiting out a real interval. The VMC's *only* lease relationship is the `in_maintenance()` boolean read in `deposit_funds`, plus `make_idle_for_service()` itself -- the one FSM operation (refund the right amount, cancel a live sale, cancel the session timer, per state) the lease cannot do for itself, which `begin_standby` calls back through. `lease` is the public read-only `@property` over `MaintenanceLease` on `Machine`; routes and tests read `machine.lease.hold`/`.idle_task`/`.sweep_task` directly (`machine.maintenance_hold` stays as its own public convenience, equivalent to `machine.lease.hold`), and mutate only through `machine.lease.begin_maintenance`/`begin_standby`/`end_maintenance`/`take_over_maintenance`/`release(...)` -- never by assigning to it directly. `POST /tests/sale` (`packages/edge/src/ice_edge/web/routes/tests_level/sale.py`) catches the resulting `RuntimeError` as a normal refusal rendered via `partials/test_refusal.html`, not a 500.

**FIFO method attribution:** `escrow_credits` is a FIFO ledger of `Credit(method, amount, ts)` that backs `credit_escrow`, which remains the authoritative total. Deducting a sale's price consumes credits first-in-first-out (`EscrowLedger.consume_fifo`) and records the per-method shares on `pending_sale_shares`; `vend_failed` restores **exactly those shares as separate credits with their original methods**, so money is never reclassified when a sale fails. Method strings are stored raw from `PaymentEvent.method` and classified only at query time. If the ledger and the total ever disagree the sale is booked to `{"unknown": price}` with a warning — a bug guard, not a path. The ledger itself lives in `packages/edge/src/ice_edge/ledger/escrow_ledger.py`'s `EscrowLedger` (the second piece carved off the VMC god object, after `FaultRegistry`); `credit_escrow`/`escrow_credits` stay public read/write conveniences on the VMC over the ledger's `total`/`credits` (the divergence guard inside `EscrowLedger.consume_fifo` still only ever sees them move together), and `escrow` is the public read-only `@property` over the `EscrowLedger` object itself for callers that want it (e.g. `vmc.escrow.is_empty_within_tolerance`).

**Refund protocol extraction:** the refund request → ack → one retry (same `request_id`) → `PAY-103` state machine lives in `packages/edge/src/ice_edge/payment/refund_protocol.py`'s `RefundProtocol`, built by `Machine` (the third piece carved off the VMC god object, after `FaultRegistry` and `EscrowLedger`). `VMC.request_refund` and `on_refund_ack` are the entry points — the former hands the registry's own amount/reason to `self._refunds.begin(...)`, the latter validates the MQTT payload and hands the result to `self._refunds.handle_ack(...)` — while the terminal side effects (persisting the session, then the `SaleJournal` calls that write the transaction-log lines, `refund`/`refund_failed` rows and customer message, and raising `PAY-103`) stay on the VMC as the `on_confirmed`/`on_failed` callbacks (`_refund_confirmed`/`_refund_failed`) `Machine` constructs the protocol with. The retry deliberately reuses the SAME `request_id` rather than minting a fresh one — the subsystems dedupe on it and replay a cached ack instead of re-running the handler, exactly like the `command_dispatcher` retry described above; a fresh id would repeat a real-world side effect. `refunds` is the public read-only `@property` over the `RefundProtocol` itself; tests read `vmc.refunds.pending` directly rather than a VMC-private alias, and mutate only through `request_refund`/`on_refund_ack`.

**Session recovery extraction:** the PAY-104 read-and-decide half of crash recovery lives in `packages/edge/src/ice_edge/ledger/session_recovery.py`'s `SessionRecovery` (the fourth piece carved off the VMC god object, after `FaultRegistry`, `EscrowLedger`, and `RefundProtocol`), owned by `Machine`, not the VMC. It owns the boot-time three-way decision over a loaded snapshot (`evaluate_at_boot()` returns a `BootDecision` of `discard_test`/`uncertain`/`closed`/`none`, performing `SessionStore.clear()` itself for the two discard cases) plus the read-only `pending_sale_for_recovery()` accessor and its record-once guards (`_pay104_sale_key`, `pending_sale_already_recorded`, `reserve_pending_sale`, `mark_pending_sale_recorded`) — `_recorded_pay104_keys` is this class's own state, lost on restart by design. The VMC keeps only snapshot building (`_snapshot`/`snapshot()`); `Machine.set_session_store` runs the boot evaluation and its own side effects (`_flag_uncertain_session` on `uncertain`; the warning log on `discard_test`), and the four public recovery methods (`pending_sale_for_recovery`, `pending_sale_already_recorded`, `reserve_pending_sale`, `mark_pending_sale_recorded`) are one-line forwards on `Machine` that routes and 20+ tests call as `machine.<method>()`, not `vmc.<method>()`. The `is_test` chokepoints described above live in `SessionRecovery.evaluate_at_boot` and `SessionRecovery.pending_sale_for_recovery`; the guarantee is unchanged.

**Telemetry router extraction:** every inbound MQTT handler that only reads/validates its payload and forwards it to the health monitor, availability, or a log sink — hardware IO, payment status, sensor/water-flow/telemetry readings, heartbeats, ice-maker events, command acks, and capabilities — lives in `packages/edge/src/ice_edge/hal/mqtt_inbound.py`'s `TelemetryRouter` (the fifth piece carved off the VMC god object, after `FaultRegistry`, `EscrowLedger`, `RefundProtocol`, and `SessionRecovery`), owned by `Machine`. The nine `handle_*` methods replace the VMC's old one-line `async` delegates outright — there is no VMC forward left for any of them; `SUBSCRIPTIONS` resolves each topic straight to `machine.telemetry.handle_*` or `machine.vmc.on_*` (see the `Machine` paragraph above). The two handlers with a side effect reaching back into FSM/fault state are wired by `Machine` directly to the collaborator that owns it, not through the VMC: the ICE-101 auto-clear inside hardware IO is `on_bin_half_full=self._faults.clear_ice101_lockouts`, and the dispenser-profiles reconcile inside capabilities is `on_capabilities_validated=self._gate.on_vending_capabilities`.

**Task runner extraction:** the asyncio task plumbing — fire-and-forget tasks with failure logging, delayed callbacks, and the persistent-task set drained (not cancelled) at shutdown — lives in `packages/edge/src/ice_edge/supervisor/task_runner.py`'s `TaskRunner`, pure event-loop bookkeeping with no domain knowledge. `VMC._schedule` is a one-line delegate onto `self._tasks`; `drain_persistence` and `cancel_pending_tasks` live on `Machine` instead — `Machine.cancel_pending_tasks` calls `self._tasks.cancel_pending()`, then the VMC's own `cancel_timers()` (the dispense cycle's timer and the session timeout) and `RefundProtocol.cancel_all()`. `tasks` is the public read-only `@property` over the `TaskRunner` itself on `machine`; tests read `machine.tasks.loop`/`.pending`/`.persist` directly, and the `machine_fake_time`/`vmc_fake_time` fixtures construct `Machine(config, tasks=FakeTaskRunner())` in place of a real one.

The dashboard uses cookie-based session auth via `packages/edge/src/ice_edge/access/access.py`'s `AccessStore`,
persisted in `data/access.json` (mode 0600). Users have four roles (`owner`,
`secretary`, `tech`, `loader`) and a 4–8 digit PIN. First login on a new device
requires a second factor: a 6-digit OTP sent by email (when
`communication.email_gateway` is configured) or an 8-digit emergency code,
which works offline. On first boot, setup mode redirects every route to `/setup`
behind a code that exists only at the machine. The `Backoff` class enforces
exponential back-off per `(kind, subject, client)` tuple plus a per-user budget
for untrusted clients — no hard caps. Every route is gated by `require(Permission)`;
templates receive `perms` and `current_user` via `template_context` so the server
does not render controls it would refuse. POST routes require the `HX-Request`
header (HTMX's own requests set it), which blocks a plain cross-site form post
as a CSRF guard. The Tailwind config sets `future.hoverOnlyWhenSupported` so hover-only styles don't stick after a touch tap. Secrets on Settings pages are masked: a placeholder is rendered for a field that is already set, and posting the unchanged placeholder leaves the stored value alone. The MQTT page shows the effective value and disables the field when an env override is active, and never writes an env value into `config.json`. `partials/confirm_button.html` (Task 5) is the server-rendered two-tap confirm used by Controls, the Health fault Clear and the Users code Regenerate, with **no JavaScript state**. Parameters: `label`, `confirm_label`, `post_url`, `target` (an `#id` selector), `confirm_url`, and optional `confirming` (default false). The first tap `hx-get`s `confirm_url`, which the including route renders in its confirming state; the second tap `hx-post`s `post_url`. Cancel re-`hx-get`s `confirm_url` with `confirming=false` — so **any route backing a confirm button must honour that query parameter**: absent or anything but the literal string `"false"` renders the Confirm/Cancel pair, `"false"` renders the plain first-tap button.

`POST /inventory/{sku}/adjust` (the Inventory restock level, `packages/edge/src/ice_edge/web/routes/inventory.py`) takes one form field, `delta`, accepting exactly `-10`, `-1`, `1`, `10` (a loader tapping the four adjust buttons); anything else — including a non-integer string — returns **400** with the stored count unchanged. A valid delta **clamps the count at zero** rather than erroring, so tapping `-10` on a count of 3 lands on 0 — deliberately different from the Products placement form (`POST /products/{sku}/placement`), which *rejects* a typed negative count outright and leaves the stored value unchanged.

The Health level is split across six sub-levels rather than one merged page. `/health` itself shows only a four-tile summary (Subsystems, Faults, Availability, Logs) plus the VMC's own build identity from `packages/common/src/ice_common/build_info.py` (image env vars set by CI, or `git` when run from a checkout). `/health/subsystems` and `/health/subsystems/{name}` show heartbeats (liveness, uptime) and each subsystem's retained `capabilities/<subsystem>` document (`SubsystemCapabilities`: firmware, contract version, brand/model, hardware_id, ip) — subsystems in `EXPECTED_SUBSYSTEMS` are listed even before they speak. `/health/subsystems/{name}` (subsystem-windows design) renders the identity card as before, then a `#live` wrapper (`health_subsystem.html`) that owns every htmx attribute — `hx-get`, `hx-trigger="load, every 2s"`, `hx-target="this"`, innerHTML swap — around `partials/subsystem_live.html`, which itself carries no `hx-` attribute; `GET /health/subsystems/{name}/live` re-renders just that fragment, shared with the page route through `_window_context` (`packages/edge/src/ice_edge/web/routes/health/subsystems.py`) so the first paint and every poll agree. The window renders only the channels the board declares in its retained `capabilities/<name>` document (`ChannelDescriptor.direction` input/output, `driven_by`) — Inputs and Outputs sections, each either a row per declared channel or "Nothing declared by this board." Digital inputs render as circles (`rounded-full`) and digital outputs as squares (`rounded-md`), tinted green (on), red (off), or gray (board not alive, or the channel never reported); analog (temperature/counter) rows are gated the same way and show value, unit, and (for temperature) an OK/Out-of-range word. Dwell time ("on for 12 s" / "off since VMC start") comes from `HealthMonitor.record_signal`'s in-memory transition tracking — "since VMC start" until the first observed change, reset on every VMC restart. A reading is attributed to a board by `HealthMonitor.declaring_subsystem` (matched by channel id, and kind when given) scanning stored capabilities; a reading no board declares is still consumed for control but never shown. An output or input whose `driven_by` names a command the VMC would currently refuse is marked inhibited (`ring-dashed` plus the word "inhibited") via `Availability.command_inhibited` for `dispense`/`water_valve`/`payment/enable`. The view model is built by the pure helper `packages/ui/src/ice_ui/views/subsystem_window.py`'s `build_window`. Channel ids are unique within a board (the ice maker's binary output is `compressor_run`, derived from `power_on`/`power_off` events, precisely because `compressor` was already its discharge-temperature input), but `declaring_subsystem` still matches by `(id, kind)` rather than id alone so that two different boards declaring the same literal id under different kinds can never steal each other's readings. `/health/faults` lists active faults with a Clear action (gated on `clear_faults`, the two-tap confirm above); `/health/availability` shows the permissive truth table and payment-blocking reasons; `/health/logs` (gated on `view_logs`) shows the last **50** lines of `LOGS/vmc.log` (`context.tail`), not the pre-v2 fragment's 10.

The Tests level (`packages/edge/src/ice_edge/web/routes/tests_level/`) lets a tech prove a subsystem works without making a real sale, and the machine cannot sell while they do it. `/tests` shows one card per `EXPECTED_SUBSYSTEMS` entry plus the service-state card (always rendered), but is itself read-only — the GET routes (`/tests`, `/tests/log`, `/tests/sale`, `/tests/{subsystem}`) never call `machine.lease.begin_maintenance`; only a POST action acquires the lease. `POST /tests/{subsystem}/{command:path}` runs one command test after re-checking `command in testable_commands(subsystem, row["commands"])` — the intersection of `ice_contracts.board.common.TESTABLE_COMMANDS` (below) with what that subsystem's live capabilities doc advertises — against a **freshly re-read** `_subsystem_summary()`, never trusting which buttons the client was shown; an unlisted command (`refund`, `payment/enable`, `set_interval`) is refused with **403** before the lease is ever touched or the dispatcher ever called. `POST /tests/run-all` runs `ping` then `self_test` against every alive subsystem **in sequence** (one `await` at a time, never `asyncio.gather`, so two subsystems' commands can never interleave on the wire). `POST /tests/sale` runs `machine.test_sales.run_test_sale` for a form-submitted SKU; `POST /tests/end` and `POST /tests/takeover` release or transfer the caller's lease; `POST /tests/runs/{run_id}/verdict` records pass/fail plus a note on a `test_run` log row via `EventRecorder.update_metadata`. `TESTABLE_COMMANDS` (`packages/contracts/src/ice_contracts/board/common.py`) is a **server-side allowlist**, per subsystem, of exactly the standard commands (`ping`, `self_test`, `force_report`) plus that subsystem's actuator commands — it is deliberately narrower than what a subsystem's capabilities document may advertise, so a control command like `refund` or `payment/enable` can never be invoked from the Tests tile even if it shows up in capabilities. The allowlist re-check on POST is the actual security boundary here, not which buttons the template renders — a crafted request to an unlisted command still gets 403 from the server, never a silent 404 that would look like the command doesn't exist. When any test is refused because the machine is busy, `_acquire_lease_or_refusal` (`packages/edge/src/ice_edge/web/routes/tests_level/lease.py`) remaps the two opportunistic-lease refusals ("machine is mid-sale", "credit is still on the machine") to "machine is busy — take it out of service first", pointing the operator at the `POST /tests/standby` button; the "held by <id>" wording stays unchanged. The Home hero shows "Out of service — maintenance by <name>" (via `context.health_snapshot()`'s `maintenance` field, packages/edge/src/ice_edge/web/context.py:280) when `SVC-102` is active and a holder exists, without changing `is_healthy`.

### Services (`ice_edge` layers)

- `payment_gateway_manager.py` - manages Stripe/PayPal/Square gateways, generates QR codes via `qrcode` library
- `config_store.py` - persists config changes (add/update products) back to `config.json`
- `access.py` - session auth with roles, PINs, devices, emergency codes, and back-off; persists to `data/access.json`
- `mailer.py` - sends OTP and setup-code emails via SMTP
- `fsm_control.py` - translates admin commands (restart, reset, shutdown) into actions
- `availability.py` - permissive truth table (ROADMAP §3) split into three
  gates: `safety` rows block payment and sales, `fulfillment` rows block only
  the individual sale, `alert` rows block nothing. Publishes
  `cmd/payment/enable` on change; feeds the health tab and `/screen`. Only the
  seven codes in `ice_contracts.board.vending_machine.PAYMENT_BLOCKING_FAULTS` can
  inhibit payment. `product_sellable`/`sale_available` take an optional
  `ignore_faults` set that exempts named blocking codes from the
  `no_critical_fault` row for that call only, never from `payment_enabled`;
  `test_sale_sellable` is the one production caller, exempting a maintenance
  test sale from its own lease's `SVC-102` alone — see FSM Core's maintenance
  lease paragraphs above. `command_inhibited(command)` (subsystem-windows
  design) is a pure read of the already-computed rows — no recompute, no
  publish — answering whether the VMC would currently refuse `dispense`,
  `water_valve`, or `payment/enable`; a subsystem window's output/input
  signal is inhibited iff its declared `driven_by` names a command this
  returns true for.
- `health_monitor.py` - per-board signal store (subsystem-windows design):
  `record_signal(subsystem, channel_id, value, *, text=None)` tracks each
  declared channel's latest value plus binary transition/dwell timing
  in-memory (reset on restart); `declaring_subsystem(channel_id, kind=None)`
  attributes a reading to the one board whose stored `capabilities/<name>`
  document declares that channel; `record_temperature`/`record_channel` call
  through it so readings for undeclared channels are still consumed for
  control and alerting but never shown on a window; `temp_range` feeds the
  in-range check for temperature rows.
- `session_store.py` - atomic snapshot of the live sale in `data/session.json`;
  an open snapshot at boot raises `PAY-104`, which alerts the operator and
  holds the evidence file until an admin clears it, but never inhibits payment
- `command_dispatcher.py` - one `CommandDispatcher`, constructed in `ice_edge/__main__.py`
  and handed to both the VMC (`Machine.set_command_dispatcher`) and the routes
  (`routes.set_command_dispatcher`); it registers `cmd/+/ack` **once** and
  correlates each ack to its command by `request_id`. A timeout retries
  **exactly once, with the same `request_id`** — never a fresh one — because
  every subsystem (`packages/sims/src/ice_sims/base.py`) caches its last 32 acked
  `request_id`s and replays the cached ack instead of re-running the
  handler, so a retry with a new id would repeat a real-world side effect
  (a second `dispense` cycle) instead of just asking again. Raises
  `CommandTimeout(subsystem, command)` immediately when the broker is
  disconnected, without waiting out the timeout first.
- `mqtt_client.py` - the MQTT client wrapper; `subscribed` is a read-only property, true once every registered topic's subscribe has been acknowledged on the current connection (false initially, on disconnect, and in `run()`'s error paths) -- tests wait on it before publishing a non-retained message the VMC must receive
- `paths.py` - `LOG_DIR`, `LOG_FILE`, `DATA_DIR` shared by main, routes and services
- `auth_policy.py` - PIN policy (`pin_problem`); validates 4–8 digits with no repeats or runs; identifies loopback hosts (`is_loopback`)
- `event_recorder.py` - records heartbeats, refunds, vend failures, and sales to a durable SQLite schema; `sales` and `cash_collections` are never pruned, while `events` keeps a 90-day retention window via `_prune_with` (which touches only the `events` table); `db_path` is the public read-only property for the live database file, including after a `DATA-102` corrupt-rename fallback switches it
- `reports.py` - five report queries (`by_period`, `by_product`, `by_method`, `collections`, `summary`); window presets (`7d`, `30d`, `90d`, `12m`, `all`) via `resolve_window` (unknown values fall back to `30d`); CSV rendering via `render_csv` (returns **bytes**); and report filename via `report_filename`. All functions are **synchronous** and called from routes through `asyncio.to_thread`; each calls `recorder.flush()` first
- `report_scheduler.py` - a supervised loop with a **bounded sleep of at most 60 s**, re-reading the live `config` each pass so turning the schedule off stops the next send within a minute; **per-period de-duplication** via a `report_sent` event, matching **any** stored event for the period rather than only the most recent; and **at most one catch-up** at startup for the most recent completed period, never a backlog. A failed send waits for the next due occurrence rather than retrying every pass

### Hardware

There is no in-process hardware code; real MDB and I/O live on the ESP32 boards and arrive over MQTT (simulated by `packages/sims/src/ice_sims/`).

### Docker

`Dockerfile` builds from `python:3.12-slim`, installs dependencies with
`uv sync --frozen --no-dev` from `pyproject.toml`/`uv.lock`, and runs
`uv run python -m ice_edge` (port 26123). `docker-compose.yml` orchestrates the VMC,
the three ESP32 simulators, and a mosquitto broker, all with
`restart: unless-stopped`. There is no `requirements.txt` — `pyproject.toml` is
the single dependency source of truth. Inside compose, config lives at
`data/config.json` (bind-mounted `./data:/app/data`, writable for the `vmc`
service and read-only for the simulators), pointed to via `ICE_COLDER_CONFIG`
in each service's `environment` — not bind-mounted directly as
`config.json`, since that file is gitignored and doesn't exist on a fresh
clone.

CI/CD: `.github/workflows/ci.yml` runs ruff and pytest on every push/PR and,
on `main`, publishes the image to `ghcr.io/conradstorz/ice-colder` (`latest`
and `sha-<commit>`). Compose services reference that image (with `build: .`
kept for local `--build`) and carry the Watchtower enable label, so the
simulation host updates itself; `docker compose pull` then `up -d` forces it.
A `compose-config` CI job runs `docker compose config` against both compose
files with `.env.example` to catch YAML/interpolation errors before `image`
builds.

Both the root `docker-compose.yml` and `docker/docker-compose.prod.yml`
require a `.env` file (`cp .env.example .env`) and run a one-shot
`mosquitto-init` service that writes the broker's password file from it
before `mosquitto` starts; `docker/docker-compose.yml` stays an anonymous
broker for local development only. `mosquitto-init` rewrites that file from
`.env` on every start (`mosquitto_passwd -c`), so accounts added by hand are
discarded on the next `up`; the optional `HA_MQTT_USERNAME`/`HA_MQTT_PASSWORD`
pair adds a second account for Home Assistant and is skipped when the password
is empty. `MQTT_USERNAME`/`MQTT_PASSWORD` from
`.env` are passed into the VMC and simulators and read by
`ice_edge.config.env_overrides.apply_env_overrides` (re-exported by `ice_edge.app.startup_config`), which returns an `EnvOverrides`
(a `model_copy` of `config.mqtt` with env values applied, plus the resolved
trusted-proxies list) without mutating the live `ConfigModel` — so an env-only
`MQTT_PASSWORD` can never be written back to `config.json` by a later
`save_config`. `ICE_COLDER_TRUSTED_PROXIES` is resolved the same way and
applied to the dashboard's login back-off via
`routes.backoff.set_trusted_proxies(...)`, called after
`routes.set_config_object(...)` so the env value wins.

## Cloud (`ice_cloud`)

A runnable, **dev-only, no-auth** fleet portal stub: `packages/cloud`, spec `docs/superpowers/specs/2026-10-13-cloud-monitoring-server-design.md`. It binds `127.0.0.1` by default (compose maps `127.0.0.1:26124`); never expose it beyond localhost until auth and mTLS exist (spec §8).

- Machines push `MachineReport`s (`POST /api/v1/machines/{id}/report`) and UI bundles (`PUT /api/v1/ui-bundles/{digest}`) from `ice_edge.uplink` (`cloud.enabled` defaults to false); data lives in `ICE_CLOUD_DATA` (default `./cloud_data`, gitignored).
- The portal renders the machine's **own** `ice_ui` templates from the last stored report at the same paths (`/`, `/status`, `/pill`, `/kpi`, `/health`, `/health/faults`), read-only (`REMOTE_VIEWER_PERMISSIONS`), under an Offline banner when the report is older than 3 x its interval. Any other page is 404 "Not available remotely yet".
- Reported UI digest = installed `ice_ui` -> installed UI; a cached uploaded bundle -> rendered in a `SandboxedEnvironment`; unknown -> installed UI plus a mismatch banner.
- `tests/cloud/test_ui_parity.py` is the executable form of the parity rule: edge and cloud must render identical `<main>` (full pages) or body (fragments). `ice_cloud` may import `ice_ui`, `ice_common` and `ice_contracts`, never `ice_edge` or `ice_sims` (import-linter).
- Run: `uv run python -m ice_cloud`; image: `docker build -f packages/cloud/Dockerfile .` (its own `Dockerfile.dockerignore` overrides the root `.dockerignore`, which excludes `packages/cloud`).

## Fault Codes and Severity

`DATA-101` (sale write failed; held in fallback file) and `DATA-102` (event database was reset after corruption; history before the reset is lost) are both **alert-class** (`Severity.warning`, `Scope.machine`) and are **deliberately absent from `PAYMENT_BLOCKING_FAULTS`**. Neither fault can ever stop the machine taking money. Both are registered in `packages/contracts/src/ice_contracts/board/vending_machine.py`.

`PAYMENT_BLOCKING_FAULTS` holds **seven** codes: `ICE-402`, `WTR-103`, `WTR-104`, `ENV-102`, `ENV-103`, `PWR-102`, and `SVC-102` (the maintenance lease, above). `SVC-102` is the one member that is not `critical` severity — it is a deliberate operator-held lease rather than a hardware failure, and it clears itself the moment the lease is released; membership in the frozenset, not severity, is what gates payment.

Both contracts bumped their `CONTRACT_VERSION` for this part: `packages/contracts/src/ice_contracts/board/vending_machine.py` **0.4.0 → 0.5.0** and `packages/contracts/src/ice_contracts/board/ice_maker_monitor.py` **1.1.0 → 1.2.0**. The vending-machine bump is a minor version absorbing two additive changes: adding `SVC-102` (new `FaultCode` + `FAULT_TABLE` entry + `PAYMENT_BLOCKING_FAULTS` member, six → seven), and the `DATA-101` description wording fix above ("sale journal in use; sales are being written to a fallback file" → "sale write failed; held in fallback file") — a part 3 change that shipped without its own version bump at the time; that deferred bump is absorbed here too.

Both contracts bumped again for the subsystem-windows feature: `packages/contracts/src/ice_contracts/board/vending_machine.py` **0.6.0 → 0.7.0** and `packages/contracts/src/ice_contracts/board/ice_maker_monitor.py` **1.3.0 → 1.4.0**, for the additive `ChannelDescriptor.direction`/`driven_by` fields (new optional fields distinguishing a board's sensed inputs from its driven outputs, and naming the command whose refusal inhibits an output).

`packages/contracts/src/ice_contracts/board/vending_machine.py` bumped once more, **0.7.0 → 0.8.0**, for the dispenser-profiles feature: `CFG-101` (no valid dispenser profile for a slot; `product_unavailable` severity, `Scope.product`) and `CFG-102` (`dispensers.toml` could not be read; `warning` severity, `Scope.machine`) — neither is a member of `PAYMENT_BLOCKING_FAULTS`, so a missing or invalid profile locks only the affected product's sale, never payment machine-wide. `CFG-101` is raised and cleared by `machine.gate.reconcile()` and re-asserted by `FaultService.clear_fault` if clearing some other lockout on a still-profile-less product would otherwise leave it unlocked; `CFG-102` tracks whether `dispensers.toml` itself loaded cleanly. Plan 2 (`DispenseCommand`/`DispenseStep`, the new `DispenserOutcome` members, `fault_for_outcome`) first shipped under this same 0.8.0 version on the theory that it was additive, but a Copilot review of PR #32 found it wire-breaking (`dispense`'s params changed shape; `cmd/dispense` was removed), so `packages/contracts/src/ice_contracts/board/vending_machine.py` bumped again, **0.8.0 → 1.0.0**, a major bump per the module's own breaking-change rule. `CFG-101`/`CFG-102` themselves stay documented at 0.8.0 — only the plan-2 runtime wiring moved to 1.0.0's "Semantics fixed in 1.0.0 (breaking)" section.

## Key Patterns

- **Logging**: Uses `loguru` throughout. `packages/common/src/ice_common/logging_setup.py` owns `setup_logging()`, called explicitly at the start of `main()`; importing the module does not change handlers or create files. It configures `LOGS/vmc.log`, an INFO-level console sink, and filtered `transactions.log`, `ice_maker.log`, and `vending.log` files. File logs rotate at midnight with 300-day retention and ZIP compression. State changes are prefixed with `STATE_CHANGE_PREFIX`.
- **Config mutation**: Product changes go through `packages/edge/src/ice_edge/config/config_store.py` which writes back to `config.json`. The in-memory `ConfigModel` is mutated directly (Pydantic models with mutable fields).
- **Web UI updates**: The dashboard uses HTMX to swap HTML partials from FastAPI endpoints. No SPA framework.
- **Timezone handling**: Report bucketing uses the machine's local timezone; weeks start on **Monday**; a sale exactly on a boundary (e.g. midnight) belongs to the **later** bucket.
- **DST testing**: `zoneinfo.ZoneInfo` is **unusable on a Windows checkout without `tzdata`**, so the DST tests use synthetic `tzinfo` classes. The primary synthetic zones (`_SyntheticDstTz` and `_SyntheticFallBackTz`) are in `tests/edge/reporting/test_reports.py` (lines 24, 91) to test report bucketing across DST transitions; `tests/edge/reporting/test_report_scheduler.py` mirrors them (lines 72, 102) to verify the scheduler threads its `tz` parameter correctly. Production code uses the OS's real timezone resolver.
- **CSS class extractor limitation**: `tests/ui/test_static_css.py`'s class extractor cannot tell markup inside a Jinja2 comment (`{# ... #}`) from real markup, so a template comment containing a literal `class="..."` will fail the test. This regex-based limitation (`_CLASS_ATTR_RE` at line 25) has no comment awareness — mentioning a Tailwind class name in a comment is safe, but writing an actual `class="..."` attribute in one is not. `tests/meta/test_no_private_access.py`'s private-access ratchet does *not* share this blindness: it walks the `ast`, so private names in comments and docstrings are ignored.

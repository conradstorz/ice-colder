## 0.3.0: cloud alert handling (additive)

`RegisterResponse` gains one field, `alerts_handled: bool = false`. It is `true` when the machine is claimed **and** the cloud has SMTP configured, meaning the cloud emails this machine's alerts. The edge then defers its own local alert emails (the cooldown bookkeeping still runs) only while it is fresh: the last successful report is within 3 x `report_interval_seconds`, so an unreachable cloud is covered by local email again within about three minutes. The edge keeps the flag in memory only: it is cleared on a 401 or a failed register and set afresh by each successful register response. Semantics: `docs/superpowers/specs/2026-10-19-cloud-alert-forwarding-design.md` section 4.

`CLOUD_CONTRACT_VERSION` is `"0.3.0"`; the edge sends it in `MachineReport.contract`. `MachineReport.contract` accepts `"0.2.0"` and `"0.3.0"`, so the cloud keeps ingesting reports from edges that have not been upgraded. No other wire change.

## 0.2.0: machine identity

Machines authenticate with an Ed25519 key they generate (`data/cloud_identity.json`). Machine identity is the **fingerprint**, the lower-case hex SHA-256 of the raw 32-byte public key; the config `machine_id` is only a display label. Models: `ice_contracts.cloud.identity` (`RegisterMachine{public_key_b64, label}`, `RegisterResponse{fingerprint, claimed, alerts_handled}`, `ClaimCodeNotice{claim_code_hash, expires_at | null}`; null = a setup code that never expires). Signing helpers: `ice_contracts.cloud.signing`.

**Signature.** Every `/api/v1/machines/*` request and the bundle `PUT` carries:

| Header | Value |
|---|---|
| `X-Ice-Machine` | full fingerprint |
| `X-Ice-Timestamp` | ISO-8601 UTC, seconds; must be within 300 s of the server clock |
| `X-Ice-Signature` | base64 Ed25519 signature over `"{METHOD}\n{path}\n{timestamp}\n{sha256_hex(body)}"` (UTF-8) |

`path` is the request path only (no scheme, host or query), exactly as the cloud app sees it (`request.url.path`); a deployment behind a path prefix must strip the prefix at the proxy.

**Endpoints** (prefix `/api/v1`):

| Request | Success | Notes |
|---|---|---|
| `POST /machines/register` (`RegisterMachine`, signed with the key in the body) | 200 `RegisterResponse` (`alerts_handled` since 0.3.0) | First call inserts an unclaimed machine; a repeat updates `label` and `last_seen_at` only. The header fingerprint must equal the body key's. |
| `POST /machines/{fingerprint}/report` (`MachineReport`, `contract` `"0.3.0"`; `"0.2.0"` is still accepted) | 204 | Path fingerprint must equal the authenticated machine's. Report body otherwise unchanged. |
| `POST /machines/{fingerprint}/claim-code` (`ClaimCodeNotice`) | 204 | Sets the live claim-code hash. |
| `DELETE /machines/{fingerprint}/claim-code` | 204 | Clears it. |
| `PUT /ui-bundles/{digest}` (bundle zip) | 201 new, 200 already held | Requires a registered machine. 400 with `{"detail"}` for an invalid bundle. |

**Errors.** Any authentication failure (missing header, stale timestamp, unknown fingerprint, bad signature, path fingerprint mismatch) is **401 with an empty body**. A body over the limit is **413 with an empty body**, decided as bytes arrive, before routing or auth: 20 MiB for the bundle `PUT`, 256 KiB for every other request. An invalid body is 422, except on `register`, where it is 401.

**Claiming** is not part of this machine contract: the owner enters the short fingerprint and the code minted at the machine on the cloud's `/claim` page; the cloud compares against the hash received in the claim-code notice.

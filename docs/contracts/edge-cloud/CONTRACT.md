# Edge-cloud contract v1.0.0

`MachineReport` (what a machine uploads) and `BundleManifest` (the `manifest.json` of an uploaded UI bundle).

- Models: `ice_contracts.cloud.report`, `ice_contracts.cloud.ui` (`CLOUD_CONTRACT_VERSION = "1.0.0"`).
- Schemas: `schemas/*.schema.json`, generated by `uv run python -m ice_contracts.generate` and drift-tested.
- Field semantics, offline rules, transport and the JSON example: [`docs/superpowers/specs/2026-10-13-cloud-monitoring-server-design.md`](../../superpowers/specs/2026-10-13-cloud-monitoring-server-design.md) sections 3 and 6.
- Versioning follows layer-contracts section 1.3. This version does not yet use the section 1.1 envelope.

## 1.0.0: money in integer cents (breaking)

Every money field is whole cents (`ice_contracts.money.Cents`, a non-negative strict integer), renamed with a `_cents` suffix:

| 0.x field (dollar float) | 1.0.0 field |
|---|---|
| `StatusView.credit_escrow` | `credit_escrow_cents` |
| `PendingSaleView.price` | `price_cents` |
| `PendingSaleView.methods` (`dict[str, float]`) | `methods` (`dict[str, Cents]`) |
| `KpiWindow.money_in` | `money_in_cents` |
| `KpiAverage.money_in` | `money_in_cents` (float cents: an average, not quantized) |

`contract` accepts `0.2.0`, `0.3.0`, `0.4.0` and `1.0.0`. Each of the four models has a before-validator that converts the old dollar key when the new one is absent (`dollars_to_cents`, half-even; `KpiAverage` multiplies by 100 as a float), so stored 0.x snapshots and alert rows still read. The edge always sends `"1.0.0"`.

**Deploy order: cloud first.** A 0.4.0 cloud answers a 1.0.0 report with 422 and the uplink retries each interval until the cloud is upgraded. Uploaded UI bundles built before 1.0.0 read dollar names; the cloud portal detects such a bundle once, when it first resolves it (a template under `templates/` still reading `status.credit_escrow`, `.money_in` or `pending_sale.price`; the manifest's `ice_ui_version` was never bumped, so it cannot tell), and only then supplies `credit_escrow`, `money_in` and `pending_sale.price` dollar display aliases and converts `pending_sale.methods` to dollars in place. The installed UI and 1.0.0 bundles always read cents. The aliases go away once no 0.x edge reports.

**Rollback and release timing.** Once the cloud has rewritten stored snapshots and `faults_json` in 1.0.0 shape, it cannot be rolled back to 0.4.0 without restoring its backup (`docs/backups.md`, "Cloud: `cloud.db`"). Merging to main publishes `latest` for both the edge and cloud images, and Watchtower may pull them in any order: an edge that upgrades first gets transient 422s, which it logs and retries each interval, with no sale impact.

## 0.4.0: machine common name (additive)

`MachineReport` gains `common_name: str | None = null`, the operator-entered machine name from `physical.common_name` (clipped to 200 characters by the edge), shown on the cloud's You page and bar badge. `contract` accepts `0.2.0`, `0.3.0` and `0.4.0`. Upgrade the cloud before the edges: a 0.3.0 cloud rejects a 0.4.0 report with 422.

`CLOUD_CONTRACT_VERSION` is `"0.4.0"`; the edge sends it in `MachineReport.contract`.

## 0.3.0: cloud alert handling (additive)

`RegisterResponse` gains one field, `alerts_handled: bool = false`, and the report answer changes from `204` to `200` with a new `ReportResponse{alerts_handled: bool}` body. The flag is recomputed by the cloud on **every** register and report and is `true` only while the machine is claimed, the cloud has SMTP configured, at least one recipient is unmuted and not suspended, and the machine's latest attempted alert delivery did not fail. The edge then defers its own local alert emails (the cooldown bookkeeping still runs) only while it is fresh: the last successful report is within 3 x `report_interval_seconds`, so an unreachable cloud is covered by local email again within about three minutes. The edge keeps the flag in memory only: it is set from each successful register or report response, and cleared on a 401, a failed register, or a report answer with no readable body (a 204 from an older cloud). `RegisterMachine.label` is 1 to 64 characters with no control characters (CR, LF and other C0 characters are rejected). Upgrade the cloud before the edges: a 0.2.0 cloud rejects a 0.3.0 report with 422. Semantics: `docs/superpowers/specs/2026-10-19-cloud-alert-forwarding-design.md` section 4.

Validation caps (no version bump; real reports are far below them): `MachineReport.faults` and `health.active_faults` hold at most 200 entries, and a fault's `key`, `sku`, `product`, `code` and `description`, and `StatusView.selected_product`, are at most 200 characters; a report over a cap is a 422. Product names and skus are operator-entered, so the edge clips those strings to 200 characters when it builds a report rather than sending one the cloud would refuse.

`CLOUD_CONTRACT_VERSION` was `"0.3.0"` at this version; the edge sent it in `MachineReport.contract`, which accepted `"0.2.0"` and `"0.3.0"`, so the cloud kept ingesting reports from edges that had not been upgraded. No other wire change.

## 0.2.0: machine identity

Machines authenticate with an Ed25519 key they generate (`data/cloud_identity.json`). Machine identity is the **fingerprint**, the lower-case hex SHA-256 of the raw 32-byte public key; the config `machine_id` is only a display label. Models: `ice_contracts.cloud.identity` (`RegisterMachine{public_key_b64, label}`, `RegisterResponse{fingerprint, claimed, alerts_handled}`, `ReportResponse{alerts_handled}`, `ClaimCodeNotice{claim_code_hash, expires_at | null}`; null = a setup code that never expires). Signing helpers: `ice_contracts.cloud.signing`.

**Signature.** Every `/api/v1/machines/*` request and the bundle `PUT` carries:

| Header | Value |
|---|---|
| `X-Ice-Machine` | full fingerprint |
| `X-Ice-Timestamp` | ISO-8601 UTC, seconds; must be within 300 s of the server clock |
| `X-Ice-Signature` | base64 Ed25519 signature over `"{METHOD}\n{path}\n{timestamp}\n{sha256_hex(body)}"` (UTF-8) |

`path` is the request path only (no scheme, host or query), exactly as the cloud app sees it (`request.url.path`); a deployment behind a path prefix must strip the prefix at the proxy.

**Endpoints** (prefix `/api/v1`):

| Request | Success | Notes |
|---|---|---|
| `POST /machines/register` (`RegisterMachine`, signed with the key in the body) | 200 `RegisterResponse` (`alerts_handled` since 0.3.0) | First call inserts an unclaimed machine; a repeat updates `label` and `last_seen_at` only. The header fingerprint must equal the body key's. |
| `POST /machines/{fingerprint}/report` (`MachineReport`, `contract` `"1.0.0"`; `"0.2.0"`, `"0.3.0"` and `"0.4.0"` are still accepted) | 200 `ReportResponse` (`alerts_handled`; `204` before 0.3.0) | Path fingerprint must equal the authenticated machine's. Report body otherwise unchanged. |
| `POST /machines/{fingerprint}/claim-code` (`ClaimCodeNotice`) | 204 | Sets the live claim-code hash. |
| `DELETE /machines/{fingerprint}/claim-code` | 204 | Clears it. |
| `PUT /ui-bundles/{digest}` (bundle zip) | 201 new, 200 already held | Requires a registered machine. 400 with `{"detail"}` for an invalid bundle. |

**Errors.** Any authentication failure (missing header, stale timestamp, unknown fingerprint, bad signature, path fingerprint mismatch) is **401 with an empty body**. A body over the limit is **413 with an empty body**, decided as bytes arrive, before routing or auth: 20 MiB for the bundle `PUT`, 256 KiB for every other request. An invalid body is 422, except on `register`, where it is 401.

**Claiming** is not part of this machine contract: the owner enters the short fingerprint and the code minted at the machine on the cloud's `/claim` page; the cloud compares against the hash received in the claim-code notice.

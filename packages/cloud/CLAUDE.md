# Cloud (`ice_cloud`)

Scoped `CLAUDE.md`, loaded when working under `packages/cloud/`. Moved from the root `CLAUDE.md`; project-wide rules stay there.

## Cloud (`ice_cloud`)

A multi-owner fleet portal: `packages/cloud` (README there), specs `docs/superpowers/specs/2026-10-13-cloud-monitoring-server-design.md` (portal, reports, bundles) and `2026-10-19-cloud-identity-tenancy-design.md` (identity; supersedes the first spec's §8 stub). It binds `127.0.0.1` by default (compose maps `127.0.0.1:26124`); HTTPS is a reverse proxy's job and the app must be served at a path root (the signature covers `request.url.path`, so a prefix must be stripped at the proxy).

- **Machine identity.** The edge generates an Ed25519 key in `data/cloud_identity.json` (`ice_edge.uplink.identity`, only when `cloud.enabled`; deleting it makes a new unclaimed machine). Identity is the key's SHA-256 fingerprint, never `machine_id` (a label); humans see the short form `xxxx-xxxx-xxxx-xxxx`, shown on `/health`, `/users/ownership`, `/setup` and `/setup/codes`, and logged once at uplink start. Every `/api/v1/machines/*` request and the bundle `PUT` carries `X-Ice-Machine`/`X-Ice-Timestamp`/`X-Ice-Signature` (`ice_contracts.cloud.signing`, 300 s skew); failure is an empty 401 (`ice_cloud.machine_auth`). Request bodies are capped by `BodyLimitMiddleware` (20 MiB bundle `PUT`, 256 KiB otherwise, empty 413); at most 2 bundle bodies are buffered at once (`MAX_INFLIGHT_BUNDLE_BODIES`), a third answers 503 with `Retry-After: 30` before its body is read. A bundle body must arrive within `BUNDLE_BODY_READ_SECONDS` (30 s) of taking its slot or the request answers an empty 408 and frees the slot, so a trickled body cannot pin both.
- **Uplink.** `run_uplink` registers (`POST /api/v1/machines/register`) before anything else, retries an unacked claim-code notice (`POST|DELETE .../{fingerprint}/claim-code`), `PUT`s the bundle (retried each pass until accepted; a 401/409 refusal is retried only after `report_interval_seconds * 60` or a new registration), then `POST`s `MachineReport`s to `.../{fingerprint}/report` every pass whether or not the bundle was accepted. A 401 sends it back to register and re-sends the bundle and live notice. Failures are logged and never touch a sale.
- **Claim codes.** Ownership is claimed at `/claim` with the code minted at the machine (setup code, transfer code, or `/users/ownership` "Link to cloud", 7 days); the cloud holds only the scrypt hash (`AccessStore.cloud_claim_code`). Claim is a compare-and-swap on the verified hash; every failure costs one scrypt and the same 403; back-off (`ice_common.backoff.Backoff`, keyed on client IP, 429) precedes the check. A claim replaces the owner and deletes tech memberships only when the owner actually changes (re-claiming your own machine keeps your techs). uvicorn trusts `X-Forwarded-For` from loopback proxies by default; when the proxy is not on loopback (a Docker bridge), claimants share one back-off bucket unless `FORWARDED_ALLOW_IPS` names the proxy. Every hash a claim consumes goes into the permanent per-machine `consumed_claim_hashes` set (only an admin unbind clears it) and `set_claim_code` ignores any hash in it, so a resale `/setup` or a fallback to the setup hash cannot reopen a spent claim; claim on the cloud before pressing Done at the machine.
- **People.** Google OIDC only (`ice_cloud.oidc`, `oidc_google`, sessions in `ice_cloud.auth`; cookie `ice_cloud_session`, short-key payload, 30 d idle / 90 d absolute). Roles are derived: owner = `machines.owner_id`, tech = a membership (owner-invited at `/machines/{short}/people`, link shown not emailed), platform admin = email in `ICE_CLOUD_ADMINS` (`/admin`: unbind, suspend). **Admin is not a machine role** (spec `docs/superpowers/specs/2026-10-24-cloud-admin-hat-design.md`): `Role` is `owner | tech`, `require_machine_access` and the selection cookie resolve membership alone, so an admin with no membership gets 404 on `/fleet/select`, `/m/{short}`, `/machines/{short}/people` and `/machines/{short}/alerts` like any stranger. A non-member gets 404 on a machine, never 403. Env (`ice_cloud.settings`): `ICE_CLOUD_SESSION_KEY` (>= 32 bytes, required), `ICE_CLOUD_PUBLIC_URL`, `ICE_CLOUD_GOOGLE_CLIENT_ID`/`_SECRET`, `ICE_CLOUD_ADMINS`, `ICE_CLOUD_INSECURE_COOKIES`, `ICE_CLOUD_DATA`, `ICE_CLOUD_HOST`.
- **Storage.** SQLite `cloud.db` in `SqliteRepository` (`ice_cloud.store`; SQL only in `store/sqlite.py`); report snapshots stay file-per-machine under `machines/`, UI bundles under `ui/` (`ICE_CLOUD_DATA`, default `./cloud_data`, gitignored). `hash_secret`/`verify_secret` live in `ice_common.secrets` (the edge re-exports both, as it does `Backoff`).
- **Alerts.** Events are derived, not sent: ingest diffs each report's `FaultView` list against the previous one kept in `machine_alert_state` (`faults_json`) -> `raised`/`cleared`; `OfflineSweep` (every 60 s, silent > 3 x interval, with a startup grace of the same length) -> `offline`, next report -> `online`. Unclaimed machines produce nothing; events and state commit together via `SqliteRepository.record_alert_pass`. Routing (`ice_cloud.alerts.router`): owner and techs get `safety`/`fulfillment` raises and offline/online, only the owner gets `alert`-gate raises, `cleared` rides along, per-person per-machine mute (`alert_prefs`, `/machines/{short}/people`). `AlertDispatcher`: one email per recipient per machine, 10-minute cooldown from the last successful send, held rows bundled (`pending`, and `failed` with < 5 attempts, fold into the next email, so callers `dispatch` then `flush`); history at `/machines/{short}/alerts`, SMTP status and test email on `/admin`. SMTP env: `ICE_CLOUD_SMTP_HOST` (unset = `LogOnlyMailer`), `_PORT` (587), `_USER`/`_PASSWORD` (user needs password), `_FROM` (required with host), `_STARTTLS` (on unless `0`). Edge fallback (contract 0.3.0): `alerts_handled` is returned on every register and every report (`POST .../report` answers `200 ReportResponse{alerts_handled}`, not 204), computed by `ice_cloud.alerts.handled.alerts_handled_for` as claimed AND SMTP configured AND at least one unmuted recipient AND `SqliteRepository.delivery_health` (latest attempted delivery not `failed`); the edge `Notifier` defers local alert email while `cloud_handles_alerts` holds (flag set from the latest accepted report/register and that report within 3 x `report_interval_seconds`) and resumes local email otherwise; the flag clears on a 401, a failed register or a report with no body (an older cloud), and `/health` shows "Alerts: cloud|local". Ingest only records events and calls `AlertDispatcher.schedule` (a tracked background task; the lifespan `drain`s it on shutdown; tests call `drain_alerts(cloud)`). Failed deliveries back off `min(2**attempts, 64)` minutes, at most 5 attempts. An owner change (or unbind) deletes alert state, prefs, events and deliveries; the cleared ride-along starts no earlier than the recipient's access start and gives techs only `safety`/`fulfillment` clears. Techs see only their own delivery lines and mute themselves on `/machines/{short}/alerts`. The offline sweep also runs `SqliteRepository.prune_alert_history` each tick, deleting alert events, settled deliveries (`sent`/`muted`/`failed` with 5+ attempts), bundle uploads and stale invitations older than `ICE_CLOUD_ALERT_RETENTION_DAYS` (default 90); `pending` rows are never pruned. Deploy the cloud before the edges (a 0.2.0 cloud answers a 0.3.0 report with 422). Contract 1.0.0 (`CLOUD_CONTRACT_VERSION`) moved every money field to integer cents (`_cents` names); `MachineReport.contract` accepts only `"1.0.0"` (0.x reports answer 422; 0.x stored snapshots read as missing until the next report), and the portal has no dollar template aliases for old uploaded bundles (removed 2026-11-02). Contract 0.4.0 adds `MachineReport.common_name` (the machine's `physical.common_name`, clipped to 200 chars), shown on `/me` and the bar badge; a 0.3.0 cloud rejects a 0.4.0 report with 422, so deploy the cloud first. Spec `docs/superpowers/specs/2026-10-19-cloud-alert-forwarding-design.md`.
- **Portal.** Renders the machine's **own** `ice_ui` templates from the last stored report at the same paths (`/`, `/status`, `/pill`, `/kpi`, `/health`, `/health/faults`), read-only (`REMOTE_VIEWER_PERMISSIONS`, owners and techs alike), after `/fleet` selection and an access check; the bar badge (`#context-badge`) reads "Cloud" on fleet-level pages and the machine label on machine pages (an "offline" tone when the report is older than 3 x its interval); there is no bottom banner. Other machine pages are 404 "Not available remotely yet". An uploaded bundle renders (in a `SandboxedEnvironment` without `request` in context, its static files under `Content-Security-Policy: sandbox`) only when its digest is the installed one or listed in `ICE_CLOUD_TRUSTED_UI_DIGESTS`; any other digest -> installed UI plus a `#ui-notice` strip under the bar. Bundle `PUT`s are accepted only from claimed machines, at most 4 distinct new digests per machine per 30 days (409), and a digest the cloud already holds is a 200 with no cap check. `GET /m/{short}` selects the machine but redirects to `/fleet`, never to a machine page. `/me` is served remotely too (`require_signed_in`, the shared `me.html`) and shows the viewer's role on the selected machine (owner / tech), or "No machine selected" with a link to `/fleet`, plus a "Platform admin" line linking to `/admin` for an admin; the login page renders no signed-in chip. **One identity, two hats, the hat is the URL:** every `/admin*` page sets the chip to `admin` and `hat_switch = MY_MACHINES_SWITCH` (a "My machines" link to `/fleet`); every other cloud page sets `hat_switch = ADMIN_SWITCH` ("Admin" → `/admin`) for an admin and nothing for anyone else (`ice_cloud.viewer`). `base.html` renders `hat_switch` as one bar link before the chip; the edge never sets it. The word "admin" never appears in the chip outside `/admin*`, and `/fleet` lists memberships only. **Bar badge:** cloud pages set the same `badge` (`badge()` and `page_context()` in `ice_cloud.context`; `_badge` in `ice_cloud.portal` picks the variant): the machine name linking to `/fleet` on machine pages, an amber "— offline" variant when the report is stale, and "Cloud" on fleet-level and `/admin*` pages. The UI-mismatch warning is the `#ui-notice` strip in the bar (replacing the old banners), and `/fleet` lists most-recently-viewed machines first via the `machine_views` table, upserted by `/fleet/select/{short}` and `/m/{short}` and deleted on unbind or owner change with the other per-machine state.
- **Admin dashboard.** `/admin` (platform admins only, 404 otherwise) is the fleet overview, polled every 60 s through the `/admin/overview` fragment; every number comes from the pure `ice_cloud.fleet_view.build_fleet_view` over stored data (no new wire data or tables). Machine status is `online` / `silent` / `never_reported`, with `STALE_FACTOR = 3` (silent beyond 3 x the report interval) defined there and read by the portal through `fleet_view.is_stale` so the dashboard and `/fleet` badges agree. Sub-levels are `/admin/machines` (filters `status`, `claimed`, `faulted`, `payment`, `owner`; Unbind lives here), `/admin/owners`, `/admin/accounts` (Suspend, SMTP status, test email) and `/admin/alerts`, in the package `ice_cloud/admin/`. Admin templates link only within `/admin` (a machine label is plain text, the alert count goes to `/admin/alerts`), because the Admin hat opens no machine page. Cloud templates are in the Tailwind content scan, so editing one means rebuilding the committed `app.css`.
- `tests/cloud/test_ui_parity.py` is the executable form of the parity rule: edge and cloud must render identical `<main>` (full pages) or body (fragments). `ice_cloud` may import `ice_ui`, `ice_common` and `ice_contracts`, never `ice_edge` or `ice_sims` (import-linter).
- Run: `uv run python -m ice_cloud` (needs `ICE_CLOUD_SESSION_KEY`); compose: `docker/docker-compose.cloud.yml` with the `ICE_CLOUD_*` block of `.env.example`; image: `docker build -f packages/cloud/Dockerfile .` (its own `Dockerfile.dockerignore` overrides the root `.dockerignore`, which excludes `packages/cloud`); CI publishes it on `main` as `ghcr.io/conradstorz/ice-colder-cloud` (`latest` and `sha-<commit>`, amd64 only), which the cloud compose file names as its `image` with the Watchtower label, so a server pulls rather than builds. `docker/docker-compose.cloud.proxy.yml` plus `docker/Caddyfile` add the HTTPS front (Caddy, Let's Encrypt for `ICE_CLOUD_DOMAIN`, `FORWARDED_ALLOW_IPS=*` so the claim back-off sees real client IPs, HSTS/nosniff/frame-deny headers, and the cloud container as uid 1000 with a read-only root filesystem and no capabilities, so the host `cloud_data` directory must be owned by uid 1000); the live deployment is the DigitalOcean droplet at `https://vmc.ohr3023.org`, files under `/opt/ice-cloud/docker/`; the runbook (host hardening, update, rebuild, claiming) is `docs/deploying-the-cloud-server.md`. Any portal link to an external origin (the Google sign-in link) must carry `hx-boost="false"`, or the shell's boosted body fetches it by XHR and the redirect dies on CORS.

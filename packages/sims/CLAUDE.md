# Simulators (`ice_sims`)

Scoped `CLAUDE.md`, loaded when working under `packages/sims/`. Moved from the root `CLAUDE.md`; project-wide rules stay there.

### Hardware

There is no in-process hardware code; real MDB and I/O live on the ESP32 boards and arrive over MQTT (simulated by `packages/sims/src/ice_sims/`). The vending simulator models the Kooler Ice IM600XL (`docs/hardware/im600xl-io-list.md`) and is split into `ice_sims.vending` modules: `board` (the `BoardPort` protocol the dispense, customer and fault modules reach the hardware through), `channels` (the one declarative channel table), `dispense` (profile execution; a profile naming an undeclared channel ends in terminal `error`), `customer` (random button presses), `faults` (data rows of the generic `ice_sims.base.InjectedFault`, whose `activate`/`recover` default to no-ops and which `set_channel(channel, on_value)` can fill; only the RO-tank faults carry real coroutines, over a `BoardPort`), `ha` (Home Assistant entities derived from the channel list), pure physical models `ro_tank` and `climate` (no MQTT, no sleep), and `simulator`, which alone composes them and owns the MQTT client and publishing; `ice_sims.vending_machine` is the thin entry module, and an `ast` test pins the single import direction (the leaf modules never import `ice_sims.base`, except `faults` and `ha`, which take the shared `InjectedFault`, `set_channel` and `uptime_entity`/`temperature_entity` from it; the mdb `faults.py` may likewise import `ice_sims.base` for `InjectedFault`; `base` never imports `vending` or `mdb`). `ice_sims.base` also owns the `ESP32Simulator.sleep`/`set_sleep` seam every board's waits go through, `publish_temperature`, and `_cache_and_publish_ack`; `ice_maker` is a `SensorFault` table (`FAULT_TABLE`) with two generic closures. The MDB payment board is simulated by `ice_sims.mdb` on payment contract 1.1.0 (`ice_sims.mdb_gateway` is its thin entry module): `cash` (coin tubes, stacker, bill escrow and the board's escrow account, pure), `policy` (the applied `set_policy`, acked per boot), `event_log` (the `payment/event` log with `boot_id`/`seq` and replay of the unacked part; it never evicts an unacked event: like the firmware it sets `pressure` at 192 pending and clears it at 128, and while set the simulator refuses coins and bills and reports `inhibited_reason: device_fault`), `customer` (the random cash customer), `faults` (injected device faults, the same `InjectedFault` rows; `changer_empty`, `board_reboot` and `drop_ack_window` keep real coroutines) and `simulator` (`MdbSimulator`: capabilities, retained `payment/state`, the `cmd/mdb` command set, payout results, the edge-silence fail-safe). Its hardware actions are public methods (`insert_coin(client, cents)`, `insert_bill`, `stack_bill`, `press_lever`), so a test can drive a customer without the random loop; `tests/integration/test_mdb_cash_sale_e2e.py` runs it against the real edge over a broker. Like the firmware (`Master::do_payout`), the simulator checks command expiry before the no-policy rejection, using the contract's default edge timeout while no policy is held. Declared channels: binary inputs `bag_full_sensor`, `button_ice`, `button_water_1gal`, `button_water_5gal`, `ro_tank_full`, `ro_tank_empty`, `water_pressure_ok`, `sump_high`, `service_door`; binary outputs `agitator_motor`, `auger_motor`, `bag_fan`, `trap_door_catch`, `water_valve_solenoid`, `ro_production`, `heater_power`; counter `fill_pulses`; temperature `ambient`. There is deliberately no `bin_half_full`, so the edge treats ice availability as uninstrumented (`Availability.bin_instrumented` false, ICE-101 retried by `ice_retry_cooldown`). The simulated RO fill loop runs `ro_production` while the tank is not full and has its own cutoff that latches until reset, which must exceed `physical.ro_max_run_seconds`.

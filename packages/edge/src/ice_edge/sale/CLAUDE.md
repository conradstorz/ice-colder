# Sale FSM collaborators (`ice_edge.sale`)

Scoped `CLAUDE.md`, loaded when working under `packages/edge/src/ice_edge/sale/`. Moved from the root `CLAUDE.md`; project-wide rules stay there.

**`StatusOutputs` (`packages/edge/src/ice_edge/sale/outputs.py`):** the FSM's only outbound channel. Methods: `state_changed(state)` (push to health and availability, persist or clear the session via `persist`, publish a retained `status` message when an MQTT client and loop both exist); `persist(state=None)` (the PAY-104 evidence guard: a no-op while `pay104_active()`, so the crash evidence file is left untouched for the operator); `save_snapshot_async(snapshot)` (the awaited save `DispenseCycle.start` uses, same guard, for a caller that is already async rather than fire-and-forget); `clear_session_evidence()`; `display(state)`; `publish_alert(alert)`. It no longer publishes anything to the payment board: the policy goes out through `PolicySync` and payouts through `PayoutProtocol`, both over the `CommandDispatcher`. A failed fire-and-forget snapshot save or clear is no longer log-only: `persist` wraps each write in a small coroutine that calls the constructor's `on_persist_failed` on an exception and `on_persist_ok` on success (`save_snapshot_async` does the same, then still re-raises to `DispenseCycle`, which raises PAY-102), and `Machine` wires them to raise `DATA-104` (once) and clear it (`by="auto"`) on the next successful write. It owns the uptime clock; every sink (`mqtt`, `health`, `availability`, `session_store`, `display_controller`) is attached later via its own `attach_*` method and defaults to `None`, so the class is fully usable with nothing wired at all. `outputs` is the public read-only `@property` over it on the VMC.

**`SaleJournal` (`packages/edge/src/ice_edge/sale/sale_journal.py`):** owns the `transaction=True`/`vending=True` bound loggers, and the `vend_failed`/`error`/`refund` recorder rows — one method per sale event. The VMC never calls `logger.bind` or `recorder.record` itself. The journal owns the sale's domain-event log lines (the bound sinks and their paired plain-logger lines), recorder rows; incidental `logger.debug` tracing and the `MQTT dispenser event` line stay at the VMC call site. `Machine` builds it right after `StatusOutputs` and passes it to `VMC` as `journal=`. `tests/meta/test_vmc_complexity.py` is a size ratchet over `packages/edge/src/ice_edge/sale/vmc.py` (class code lines, file lines, largest method code lines) whose budgets only move down and which fails when more than 10% under budget.

**Observers and `TestSaleRunner` (`packages/edge/src/ice_edge/sale/test_sale.py`):** `subscribe_state_change(cb) -> unsubscribe` and `subscribe_sale_settled(cb) -> unsubscribe` are two independent, synchronous subscriber lists on the VMC; `_after_state_change` calls `outputs.state_changed(self.state)` then every state-change observer, in subscription order, and a raising callback is logged and never stops the rest. Settled fires exactly once per sale, through `_settle` (which captures the sale before running the settling transition) at `on_dispenser_event`'s success and failure branches and `on_dispense_failed`, and through direct `_notify_settled` calls at the two sites with no legal transition to run: `on_error` (once per sale, tracked by `SaleContext.settled`) and `_dispense_succeeded`'s post-write path. The fired tuple is `(sale, outcome, fault_code)` and outcome is one of `"dispensed"`, `"vend_failed"`, `"timeout"`, `"error"` (fault code `None`; `on_error` fires it after its restore/refund so a running `TestSaleRunner` resolves and frees its lease); never fired on cancel/reset. When `on_error` runs while a settled `DispenseCycle` is still awaiting its sale write, the product is already out: shares are neither restored nor refunded, `"error"` is not fired, and `_dispense_succeeded` fires `"dispensed"` itself once the write returns (no transition, since `dispensing -> idle` is illegal from `error`); `on_error` keeps the settled cycle on the VMC so a repeated error takes the same branch, and `_dispense_succeeded` treats the sale as still its own only while `cycle is self._cycle` (a reset or a new customer's cycle makes it settle only its own sale, decrement its own stock and leave the new sale untouched). `SessionSnapshot.is_open()` is also true while `pending_sale_shares` is set, so an `error`-state snapshot of an unrecorded sale survives for PAY-104 recovery. `TestSaleRunner.run_test_sale(sku, *, user_id=None, user_name=None) -> TestSaleResult` (constructed with `vmc`, `lease`, `gate`, `recorder()`, `tasks`) talks to the VMC only through this public surface: an unknown sku raises `ValueError`; a product with no valid profile (only when `gate.profiles` is wired) raises `RuntimeError` before anything else is touched; the **double-submit guard** -- `vmc.test_sale_in_progress` -- is checked *before* `lease.test_run()` is ever entered, so a refused second call never refreshes the lease's idle clock; then `with lease.test_run():` subscribes both observers, calls `vmc.begin_test_sale(product)` (a `False` return raises the "could not select" `RuntimeError`), awaits the settlement future, appends the settled state if the path's last entry differs (the `_fail_vend` "no sellable products" branch bypasses `_after_state_change` via `vmc.set_state()` directly), records the `test_run` event row, and in `finally` unsubscribes both observers and calls `vmc.end_test_sale()` -- but only when `begin_test_sale` actually ran (the `began` flag), since one that raised its own "already in progress" guard seeded nothing for this call to clean up. `begin_test_sale` is exception-safe: anything it raises between setting the in-progress flag and returning takes the just-deposited "test" credit off escrow directly and clears the flag and the seeded `SaleContext` before propagating. A failed **test** vend always takes the credit `on_vend_failed` just restored straight off escrow (`escrow.take_all()`) inside `_fail_vend`, whether or not a runner is still awaiting it; `end_test_sale`'s own `take_all()` is a backstop, not the only path.

**A test sale is exempt from its own `SVC-102`, and only from that:** the same failing `no_critical_fault` safety row that turns the `set_policy` `accept` flag off also fails `Availability.sale_available`/`product_sellable` for an ordinary sale, so an unmodified lease would refuse the very product it exists to let a tech dispense. `product_sellable`/`sale_available` (`packages/edge/src/ice_edge/faults/availability.py`) take an `ignore_faults: frozenset[str]` (default empty, so every existing caller — including a customer's `select_product` reached during a lease — is unaffected); when every currently active blocking code is in that set, `no_critical_fault` is treated as passing for this call only, while every other row, and every other blocking code, still fails and still blocks normally. `Availability.test_sale_sellable(product)` calls it with exactly `{SVC-102}`. `VMC.select_product` picks `test_sale_sellable` over `product_sellable` when `self.sale is not None and self.sale.is_test` — the exemption is keyed on the sale, never on the lease, so a customer press reaching `select_product` during the same lease still finds `sale.is_test` false (or no sale at all), still calls `product_sellable`, and is still refused like any other safety-blocked sale. Any *other* active safety fault — a leak, a stuck trap door, a bad 24 V supply, a tripped heater high-limit — still fails `no_critical_fault` for a test sale exactly as it would a real one; running an actuator into a real hazard "because it's only a test" would be worse than the bug this fixed. `payment_enabled`/`payment_blocking_reasons` never consult `ignore_faults` — they read the rows directly — so the `set_policy` `accept` flag stays false for the entire lease regardless of which sale is attempted.

**Test-ness lives on the sale, not the hold:** `sale.is_test` is set only by `begin_test_sale` (called from `TestSaleRunner.run_test_sale`), on the `SaleContext` it seeds, and is read (never inferred from the maintenance lease) by the dispense-completion and timeout handlers to decide whether to call `DispenseCycle.record()` (skipped entirely for a test) or record a `test_run` event instead — so a test sale writes neither a `sale` nor a `dispense` row, and releasing the lease mid-run cannot reclassify it, because nothing about the recording path consults the lease. `SessionSnapshot.is_test` carries the same flag into the on-disk crash snapshot, set from `self._sale.is_test` (or, with no sale in flight, the `_test_sale_in_progress` re-entrancy guard) at the moment the snapshot is built. This is the money-safety consequence a review caught: without it, a test sale that crashed mid-dispense would leave an open snapshot that looks exactly like a real uncertain sale, and the `PAY-104` recovery flow would let an operator "Record as sale" it into the never-pruned `sales` table. `is_test` is checked at two chokepoints so that can never happen — `SessionRecovery.evaluate_at_boot()` discards a test-flagged snapshot found at boot instead of raising `PAY-104` for it at all, and `SessionRecovery.pending_sale_for_recovery()` refuses to surface one as a recoverable card even if some future path left `PAY-104` active anyway, as defence in depth. A future contributor adding a second persistence path for pending sales must carry `is_test` through it too, or this guarantee breaks silently.

**Maintenance lease (`MaintenanceHold`, `packages/edge/src/ice_edge/sale/maintenance_lease.py`'s `MaintenanceLease`, system-tests design §2.2/§2.2a):** the lease lifecycle -- the hold itself, its idle timer, the standby session-liveness sweep, and the grant/release/takeover/run accounting -- plus every FSM precondition it needs now live entirely on `MaintenanceLease`: `begin_maintenance(user_id, session_id)`, `begin_standby(user_id, session_id)`, `end_maintenance(session_id)`, and `take_over_maintenance(user_id, session_id)` all live there, taking `fsm_state() -> str`, `escrow_is_empty() -> bool`, and `make_idle_for_service() -> bool` as injected callables rather than holding a VMC reference. `begin_maintenance` grants a lease to take the machine out of service for operator testing -- refused unless the FSM is `idle`, escrow is zero, and no lease is already held; granting it raises `SVC-102` (via the lease's `on_granted` callback, which runs the VMC's `raise_fault`), which `packages/edge/src/ice_edge/faults/availability.py` treats as a **safety** row (built generically off `PAYMENT_BLOCKING_FAULTS`, not a special case), so the `set_policy` command carries `accept=false` machine-wide for the whole lease. `begin_standby` -- a lease taken explicitly by a tech to make a *busy* machine idle and hold it out of service for the whole login session (`MaintenanceHold.standby`) -- calls `make_idle_for_service()` first (refunds any credit with `reason="maintenance"`, cancels a live customer sale) rather than requiring the machine to already be idle; refused only while `dispensing` ("vend finishing, tap again") or when a different session holds the lease ("held by <id>"), and upgrades the caller's own opportunistic lease to standby in place rather than replacing it. `MaintenanceHold` is a dataclass with `runs_in_flight` (an in-progress-run counter, not a boolean) plus `release_requested`/`release_reason`: `end_maintenance` and the 5-minute idle timer (`idle_expired`) only defer a release while `runs_in_flight > 0`, and `test_run()` (a context manager `TestSaleRunner.run_test_sale` uses) increments on entry and decrements in a `finally`, so a failing or timed-out run still frees the lease. Unlike the opportunistic lease, a standby lease has no idle-timer release (`idle_expired` skips it once `hold.standby` and a liveness predicate is wired); instead a 30 s sweep (`arm_sweep`/`sweep_tick`) calls the predicate wired via `Machine.set_session_liveness(predicate)` -- `AccessStore.session_is_live`, applying the same idle-limit and absolute-cap rules as `resolve_session` but never refreshing `last_active_at` -- to check the holder's web session **without resetting its idle clock**; with no predicate wired (tests), a standby lease falls back to the ordinary idle timer. The lease is **never persisted** -- it lives only on the live `MaintenanceLease` instance (held by `Machine`) and is not part of `SessionSnapshot`, so a restart clears it. Credit arriving during a lease is **refunded, not escrowed**: `deposit_funds` reads the injected `in_maintenance()` callable and, unless the deposit's `payment_method == "test"` (the one credit `begin_test_sale` itself deposits), adds it to escrow only long enough to call `request_refund(reason="maintenance")` immediately. The three timing knobs (`MAINTENANCE_IDLE_TIMEOUT_SECONDS`, `MAINTENANCE_TAKEOVER_IDLE_SECONDS`, `STANDBY_SWEEP_SECONDS`) are `MaintenanceLease` class attributes read through injected callables, so tests shrink them per instance via `machine.lease.MAINTENANCE_IDLE_TIMEOUT_SECONDS = ...` rather than waiting out a real interval. The VMC's *only* lease relationship is the `in_maintenance()` boolean read in `deposit_funds`, plus `make_idle_for_service()` itself -- the one FSM operation (refund the right amount, cancel a live sale, cancel the session timer, per state) the lease cannot do for itself, which `begin_standby` calls back through. `lease` is the public read-only `@property` over `MaintenanceLease` on `Machine`; routes and tests read `machine.lease.hold`/`.idle_task`/`.sweep_task` directly (`machine.maintenance_hold` stays as its own public convenience, equivalent to `machine.lease.hold`), and mutate only through `machine.lease.begin_maintenance`/`begin_standby`/`end_maintenance`/`take_over_maintenance`/`release(...)` -- never by assigning to it directly. `POST /tests/sale` (`packages/edge/src/ice_edge/web/routes/tests_level/sale.py`) catches the resulting `RuntimeError` as a normal refusal rendered via `partials/test_refusal.html`, not a 500.

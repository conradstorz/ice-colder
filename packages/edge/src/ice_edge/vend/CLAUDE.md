### Dispenser profiles (`dispensers.toml`)

A standalone, hand-edited `dispensers.toml` gives each physical dispense slot (`[slot.N]`) its own mechanism parameters (agitate/fill/release timings, channel names, accessory lead/lag) — separate from `config.json`'s product catalog, which only knows a product's `sku`/`slot`/`kind`. The file lives next to `config.json` and is resolved the same way: the `ICE_COLDER_DISPENSERS` environment variable (read at call time, mirroring `_config_path`), defaulting to `dispensers.toml` in the current working directory. Like `config.json`, it is gitignored (`.gitignore`), so a fresh checkout has none; `dispensers.example.toml` is the committed, generated reference a first run copies from. Only the `vmc` compose service sets `ICE_COLDER_DISPENSERS=/app/data/dispensers.toml` — the VMC is the only reader: it sends a product's whole validated `SlotProfile` inside the `DispenseCommand` it dispatches, so the simulators never read the file themselves and their copy of the env var (present through plan 1) was removed once plan 2 shipped the runtime wiring below.

Four modules split the work. `packages/contracts/src/ice_contracts/board/dispenser_schema.py` holds the Pydantic models for one slot's profile (`SlotProfile`, a discriminated union of `BaggedIceProfile`/`WaterFillProfile`) plus the per-mechanism step models (agitate/fill/release, accessories) and helpers (`drive_channels`, `sense_channels`, `worst_case_seconds`, `MECHANISM_FOR_KIND`). `packages/edge/src/ice_edge/vend/dispensers.py` owns validation and file I/O: `validate_document(text, products, capabilities=None, dispense_timeout_seconds=120.0)` runs TOML parsing, per-slot schema validation, and cross-checks (catalog sku/slot/kind agreement, channel drive/sense conflicts, the dispense time budget, and — when a vending board's capabilities are known — channel direction) into a `ValidationReport` (`.findings`/`.errors`/`.warnings`/`.ok`/`.file_error`/`.render_text()`, each a list of `Finding(slot, path, line, severity, message)`); `DispenserProfiles(config, path=None)` wraps that with `.load()`, `.validate_text()`, `.save_text()` (atomic, digest-guarded), `.profile_for_slot()`, and `.set_capabilities()`. `packages/edge/src/ice_edge/vend/dispensers_doc.py` generates `dispensers.example.toml` from the schema's own field metadata (descriptions, units, ranges, discriminator tags) so the example cannot drift from the schema it documents. `packages/edge/src/ice_edge/vend/schema_introspect.py` holds the pydantic-schema introspection (unwrapping `Annotated`, walking unions, reading numeric bounds) shared by `dispensers` and `dispensers_doc`, with the discriminator tags derived from the schema itself; regenerate it with `uv run python scripts/gen_dispensers_example.py` after any schema or sample-value change, and `tests/edge/vend/test_dispensers_example.py` fails CI on byte drift. `uv run python -m ice_edge.vend` (`vend/__main__.py`, which does its own read-only config load because `vend` sits below `app` in the import-linter layers) with `--check` validates the active file against the live catalog and prints a human-readable report (exit 1 on any error); `--example` prints the generated reference instead.

`CFG-101` (no valid dispenser profile for a slot, product-scope, `product_unavailable`) and `CFG-102` (`dispensers.toml` could not be read, machine-scope, `warning`) are registered in `packages/contracts/src/ice_contracts/board/vending_machine.py` (contract version 0.8.0). The file is loaded and its `ValidationReport` logged at startup (`ice_edge.app.startup_dispensers.load_dispenser_profiles`, called from `main()` right after `load_config()`; each finding logs at `warning` or `error` per its own severity, the verdict line at `info`; a directory at the resolved path logs a clear error and `sys.exit(1)`, mirroring `load_config`'s own check). The loaded `DispenserProfiles` instance is then handed to both the VMC and the routes module by `ice_edge.app.startup_dispensers.wire_dispenser_profiles(machine, profiles)`, called right after `machine.set_health_monitor(health)`. `Machine.set_dispenser_profiles(profiles)` stores it and immediately calls `reconcile_dispenser_profiles()`, which re-derives every product's `CFG-101` lockout and the machine's `CFG-102` fault from the currently loaded profiles — raising `CFG-101` for a sku with no valid profile, clearing it only when the existing lockout is `CFG-101` itself, and never touching another code's lockout. `machine.gate.profile_for(product)` is the single read path `machine.gate.reconcile()`, `DispenseCycle.start`, and `TestSaleRunner.run_test_sale` go through; `select_product` itself never calls it — it refuses a locked sku the same way it refuses any other lockout, by checking `self._faults.lockouts.get(candidate.sku)`, which `machine.gate.reconcile()` populated with `CFG-101` for that sku.

This gating lives in `packages/edge/src/ice_edge/vend/dispenser_gate.py`'s `DispenserProfileGate` — it owns the loaded `DispenserProfiles` object and `profile_for`/`reconcile`/`catalog_changed`/`on_vending_capabilities`; `Machine.set_dispenser_profiles` is a one-line delegate onto `attach`, and `gate` is the public read-only `@property` over the `DispenserProfileGate` itself on `Machine` — tests and routes read `machine.gate.profiles`/`machine.gate.profile_for(...)`/`machine.gate.reconcile()`/`machine.gate.catalog_changed()` directly. `FaultService.clear_fault`'s CFG-101 re-check goes through `self._lacks_valid_profile(sku)` (a callable `Machine` wires to `self._gate.lacks_valid_profile`) rather than reaching into the gate's internals itself.

**`DispenseCycle` (`packages/edge/src/ice_edge/vend/dispense_cycle.py`):** one instance is built, through the injected `dispense_factory`, for every entry into `dispensing`, and held as `self._cycle` until the sale leaves that state; its own *identity* is what `on_dispense_failed` uses to tell a late callback from a superseded attempt apart from the current one (`cycle is self._cycle` and `self.state == "dispensing"` must both hold). `start(snapshot_for)` looks up the slot's profile via `gate.profile_for` (keyed on the product's own stable `slot` field, never its list position), mints `request_id` synchronously -- before any task exists, so no hardware report can race it -- arms the `dispense_timeout` timer, and fires the actual dispatch (`_run`) as a fire-and-forget task: `_run` awaits persisting the dispensing snapshot through `outputs.save_snapshot_async` (the PAY-104 evidence guard), then dispatches `dispense` through the command dispatcher with that `request_id` and checks the ack status -- all *after* the timer is already armed, which is exactly why a slow or failing dispatch can race the timeout and why the cycle-identity guard above exists. Every failure on that path -- no valid profile (`CFG-101`, `"no_profile"`), the snapshot save raising, no dispatcher wired, `CommandTimeout`, any other exception, or a non-`"ok"` ack -- calls `on_failed(cycle, code, outcome)` with `PAY-102` and the matching outcome string (`snapshot_failed`/`no_ack`), rather than waiting out the 120 s timeout fallback; the timer itself calls `on_failed(cycle, FaultCode.PAY_102, "no_report")`. `classify(data) -> DispenseReport | None` runs the slot-mismatch check, the `request_id` mismatch check (a report with no id at all is still accepted, keyed on slot alone), decides `door_open` is a customer success only when `(mechanism, door_open)` has an `OUTCOME_FAULTS` entry (bagged ice; never water fill), and otherwise resolves through `fault_for_outcome`, falling back to that mechanism's `error` mapping on an unmapped `(mechanism, outcome)` pair (a board mis-reporting for its own mechanism) rather than raising `KeyError` into the MQTT handler; `None` means "not for this cycle, ignore" (an intermediate step, a slot or id mismatch), and the cycle logs why. `record() -> bool` is the durable sale write: the `dispense` KPI event, then the `sales` row itself, off the loop via `asyncio.to_thread`, both skipped when no recorder is attached; price is the sum of the sale's own consumed shares, never `product.price` (an operator can edit the price mid-dispense). The sale is inserted **synchronously on its own WAL connection** (`synchronous=NORMAL`) and **awaited before the FSM returns to idle**. A generic insert failure is already journaled as a fallback by `record_sale` itself, so it raises the alert-class `DATA-101` and still returns `True`; `SaleRecordingFailed` (the insert *and* its journal fallback both failed) calls `set_transaction_certain(False)`, raises `PAY-104`, and returns `False` -- the caller's sole signal to keep `sale.shares` set so the on-disk "dispensing" snapshot stays the sale's only record, for the operator's "Record as sale" recovery; a `True` return (no recorder, the plain success path, or the `DATA-101` path) is what lets the caller clear `sale.shares`. At startup the journal is replayed idempotently on `(ts, sku)`, each row in its own transaction, so a crash mid-replay cannot duplicate a row and one bad row cannot block the others; `packages/edge/src/ice_edge/app/startup_recovery.py` clears `DATA-101` only once the journal is actually drained (absent or empty), never on the replay function's integer return (which is `0` both for "nothing to do" and "fully drained, all duplicates or rejects"). A corrupt `events.db` is renamed aside to `events.db.corrupt-<timestamp>`, a fresh database is created, and `DATA-102` is raised so the machine keeps running. `cancel()` drops the timer; the VMC calls it on every exit from `dispensing` (`_finish_dispensing`, `on_vend_failed`, `on_reset`, `on_cancel_sale`, `on_error`, and the success path itself, before the `await record()` suspension). `CFG-101` is a standing invariant enforced at two points: `select_product` refuses a profile-less product up front via the ordinary lockout path -- the sku is already `CFG-101`-locked in `vmc.faults.lockouts` by `machine.gate.reconcile()`, so `DispenseCycle.start`'s own profile lookup should never fail -- and `start` still re-checks and fails the vend with `CFG-101` if the profile vanished between selection and dispense (a `dispensers.toml` reload racing the sale), a defensive fallback, not the primary guard. Three trade-offs here are accepted and deliberate: a dispense timeout with no report restores the credit although product may have come out (`PAY-102` is raised and a later report is ignored); a report with no `request_id` is accepted by slot alone, so old firmware can settle a new sale on the same slot; and `classify` reads `sale.product.slot` from the live catalog, so editing a slot mid-dispense turns the terminal report into a slot mismatch and a timeout. The vending simulator no longer publishes `water_flow` or motor currents (the `sensors/water_flow` topic was removed from the contract in 2.0.0); the per-fill flow-meter pulse count is its own counter channel, `fill_pulses`, published on `telemetry/vending/<id>`, which the VMC does not subscribe to. Constructor dependencies: `sale`, `dispatcher()`, `gate`, `outputs`, `faults`, `recorder()`, `set_transaction_certain`, `tasks`, `timeout_seconds()`, and the two VMC callbacks `on_failed`/`on_request_id`.

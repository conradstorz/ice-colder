# Payments (`ice_edge.payment`)

Scoped `CLAUDE.md`, loaded when working under `packages/edge/src/ice_edge/payment/`. Moved from the root `CLAUDE.md`; project-wide rules stay there.

**Payouts (`ice_edge.payment.mdb`, cutover spec `docs/superpowers/specs/2026-10-30-payment-cutover-design.md`):** money leaves the machine only as `payout` and `cash_sale` commands to the MDB board over `cmd/mdb`; there is no refund topic. `VMC.request_refund(reason, detail=None, sale_id=None)` is the single entry (`sale/payout_desk.py`'s `PayoutDesk.refund`): it takes all of escrow (`EscrowLedger.take_all`), queues the **cash** part as a `payout` through the `Payments` port (`ice_edge.payment.ports`, a `Protocol` the VMC types against; contract 5 stays unwidened), and logs a non-cash part at error with `PAY-103` `non_cash_refund`; a payout that cannot be queued puts the credits back and raises `PAY-103` `payout_not_queued`. After a recorded vend `PayoutDesk.cash_sale` queues a `cash_sale` for the sale's cash share (`cash_share(sale.shares)`), and `Machine.send_recovered_cash_sale` does the same once per sale after "Record as sale". `Machine` builds the `MdbGateway` (`ice_edge/payment/mdb/__init__.py`, the `gateway` property) after the VMC and hands the VMC a forwarding `Payments`; the gateway composes `EventIntake` (`payment/event`: parse the lenient `PaymentEventHeader` first so every event is acked, dedupe on `event_id` and `seq`, `PAY-105` on a gap, ack by `(boot_id, seq)` on `payment/event/ack` only after the deposit snapshot and the `PaymentCursorStore` cursor are on disk, then `VMC.deposit_funds(..., event_id=)`), `StateConsumer` (`payment/state` into `Availability.set_payment_state`, `PAY-106`/`PAY-107` for a bad coin changer or bill validator, "Exact change only"), `PolicySync` (`set_policy`, below), `PayoutProtocol` and `Reconciler`. `PayoutProtocol` is an ordered queue with one command in flight, awaited to its completion report through `send_and_await_completion`; `request_id` is minted at enqueue and **reused on every re-send** (the board dedupes on it and replays the stored result), so an unconfirmed payout raises `PAY-103` and is dropped, never re-sent under a new id, and an unconfirmed `cash_sale` raises `PAY-104`. The one exception is a `rejected` ack: the board did nothing and caches the rejection by `request_id`, so the item is re-minted before it is retried. A queued or in-flight item persists in `SessionSnapshot.pending_payouts`; after an uncertain boot the snapshot's items are re-queued (same ids) when `PAY-104` clears, before reconciliation is released. `PolicySync` sends `set_policy` (the policy id is a hash of its fields; `accept` follows `Availability.payment_enabled`) on connect and on every change, and treats the policy as in force only once a `payment/state` from the acked boot echoes the id; it also sends the idle ping every `EDGE_IDLE_PING_SECONDS` so the board's edge-silence fail-safe does not trip. `Reconciler` compares the board's `escrow_cents` with the edge's cash escrow once the intake has caught up, the FSM is idle, the payout queue is empty, no `PAY-104` is active and a `payment/state` newer than the last completed queue item has arrived: board > edge queues an `error` payout for the difference, edge > board raises `PAY-104`. Its timers are labelled `payout_retry`, `policy_retry`, `policy_verify` and `mdb_keepalive`. `Machine` owns the `DATA-104` raise/clear for its two sources (the session snapshot and the payment cursor), neither able to clear the other's alert. The old `RefundProtocol` (`cmd/payment/refund`, ack, one retry) no longer exists; tests read `machine.gateway.payouts.pending()` (and the other gateway properties `intake`, `policy`, `state_consumer`, `reconciler`) and mutate only through `request_refund`/`deposit_funds`.

**Evidence, boot recovery and the board's boots.** `StatusOutputs` freezes the session file on `Machine`'s `evidence_held` flag (injected as the `evidence_held` callable; `on_evidence_released` lets `clear_session_evidence` drop it), **not** on `PAY-104` being active: the flag is set only by `_flag_uncertain_session` (an uncertain boot snapshot) and by the `SaleRecordingFailed` path in `DispenseCycle.record` (via its `hold_evidence` callback; the on-disk snapshot is that sale's only record). A runtime `PAY-104` (escrow mismatch, `cash_sale` outcome from `payout.py`/`reconcile.py`) therefore holds nothing: deposits and pending payouts keep persisting, and clearing it never deletes the live session file (`clear_session_evidence` removes the file only while evidence is held, then releases the flag). The `FAULT_TABLE` text for `PAY-104` still reads "Transaction uncertain after VMC restart"; it was left unchanged (a wording change would need a contract patch and regenerated docs for a cosmetic gain) and runtime causes are named in the fault's `outcome` detail. On the `closed` boot path (the snapshot's sale already has a `sales` row, so no `PAY-104`), `Machine._recover_closed_cash_sale` queues a `cash_sale` for the snapshot's cash share inside `set_session_store`, before edge-start reconciliation can evaluate, so a crash between the `sales` insert and the `cash_sale` enqueue does not pay a delivered product's price back out; the snapshot has no event ids, so the full cash share is sent (if the board rebooted it is clamped and `PAY-104` shows). Re-queued boot `cash_sale`s rely only on the board's 32-entry RAM ack cache (the firmware's `do_cash_sale` has no idempotency store), so a late duplicate is clamped and raises `PAY-104`. The board's escrow is per boot: `Reconciler` compares against `cash_cents(credits, boot_id)` (only cash credits whose `event_id` starts `<boot>-`), `PayoutDesk.cash_sale` sends only the current boot's cash (`Payments.board_boot_id()`; unknown boot counts all), and `EscrowLedger` keeps each credit's event id through consume/restore (`consume_fifo_pieces`). `PendingPayout.maybe_delivered` marks an item whose send may have reached the board (timeout, error, or restored from disk): a rejected ack for it gives up (`PAY-103` `unconfirmed:<cents>:<id>` for a payout, `PAY-104` `escrow_mismatch:cash_sale_unconfirmed` for a `cash_sale`) instead of re-minting, and the fifth `expired` rejection of one item gives up the same way.

**Payment cutover residuals (spec `2026-10-30-payment-cutover-design.md` §11):** recovery cards (`pending_sale_for_recovery`, `recovery_detail`) need `evidence_held`, not just PAY-104; `CommandNotSent` (a `CommandTimeout` subclass) marks a send that published nothing and never sets `PendingPayout.maybe_delivered`; a queued `cash_sale` carries `PendingPayout.boot_id` and is dropped (info log, no fault) if the board rebooted before it was sent; PAY-103 `unconfirmed`/`expired` outcomes read `<kind>:<cents>:<request_id>`. The closed-path boot `cash_sale` can re-send one published just before the snapshot write (visible clamp); a boot PAY-104 freezes persistence of new sales until resolved; recovery `cash_sale`s send the full cash share (the snapshot has no pieces), so a board reboot in between yields a visible clamp.

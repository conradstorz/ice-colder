# Faults (`ice_edge.faults`)

Scoped `CLAUDE.md`, loaded when working under `packages/edge/src/ice_edge/faults/`. Moved from the root `CLAUDE.md`; project-wide rules stay there.

**`FaultService` (`packages/edge/src/ice_edge/faults/fault_service.py`), wrapping `FaultRegistry` (`packages/edge/src/ice_edge/faults/fault_registry.py`):** the fault state itself -- `lockouts` (product-scope, by sku) and `machine_faults` (machine-scope, by code) -- lives in the pure `FaultRegistry`, the first piece carved off the VMC god object. `FaultService` layers every side effect on top: `raise_fault(code, *, sku=None, outcome=None)` and `clear_fault(key, by="admin")` run the event-recorder `lockout_set`/`lockout_cleared` rows, the `logger.error`/`logger.info` lines, the health-monitor alert raise/clear, the MQTT `alerts` publish, and the push of `active_faults()` to health and availability (`push_active_faults`), plus three guards -- `SVC-102` refused while the maintenance lease is held, `PAY-104` cleared only once the session evidence file is removed (then `set_transaction_certain(True)`), `CFG-101` re-raised after any lockout clear leaves a profile-less product unlocked. It also owns `on_subsystem_liveness(subsystem, alive)` (COM-101/COM-102/PAY-101 plus the availability liveness push and the MDB republish), `on_mqtt_connection(connected)` (COM-103 plus republish and status), and `clear_ice101_lockouts(by="auto")` (called by `IcePolicy` for both ICE-101 clears: `bin_half_full` true, and the `ice_retry_cooldown` timer with `by="cooldown"` when the bin is not instrumented). `ensure_raised(code, *, outcome=None) -> bool` and `ensure_cleared(code, *, by="auto") -> bool` are the idempotent machine-scope forms (raise only when inactive, clear only when active, returning whether they acted; `ensure_cleared` goes through `clear_fault`, so the SVC-102/PAY-104 guards still apply); the data-write, MDB device, input and PAY-105 sites use them, while `on_subsystem_liveness` still raises unconditionally. `subscribe_fault_change(cb)` is a generic observer of every raise/clear (`FaultChange(action, code, sku, by)`, `sku` `None` for machine-scope codes) that `IcePolicy.on_fault_change` uses to arm and cancel that timer. `IcePolicy.on_bin_instrumented(instrumented)` (fed by `IcePolicy.on_vending_capabilities` on the capabilities fan-out, deriving the flag with `availability.declares_bin_sensor`, the same helper `Availability` uses) covers the late flip: a no-bin declaration with an ICE-101 lockout already held and no timer pending arms the cooldown, and a bin-sensor declaration cancels a pending timer. Five collaborators are injected as call-time callables rather than objects, since the VMC attaches or replaces what they read after construction: `recorder`, `lease_holder`, `lacks_valid_profile` (the CFG-101 re-check, wired to `gate.lacks_valid_profile`), `set_transaction_certain`, `fsm_state`. Reads are re-exposed verbatim: `is_locked(sku)`, `has(code)`, `lockouts`, `machine_faults`, `active_faults()`, `parse_key(key)`. `VMC.raise_fault`/`clear_fault`/`active_faults` stay one-line forwards onto `self._faults`; `faults` is the public read-only `@property` over the `FaultService` itself on both `vmc` and `machine` -- tests and routes read `vmc.faults.lockouts`/`.is_locked(sku)`/`.has(code)` directly rather than a VMC-private alias, and mutate only through `raise_fault`/`clear_fault`.

**`InputFaults` (`packages/edge/src/ice_edge/faults/input_faults.py`):** subscribed to the `TelemetryRouter`'s `hardware/io` fan-out by `Machine`, it derives the water faults from the vending board's inputs. The three state faults come straight from `ice_contracts.board.vending_machine.INPUT_FAULTS` (`sump_high` true -> WTR-104, `water_pressure_ok` false -> WTR-105, `ro_tank_empty` true -> WTR-106); the opposite state clears the code. `WTR-107` is a duration rule: `ro_production` true arms the `ro_overrun` timer for `physical.ro_max_run_seconds` (default 3600, 60-86400; re-arming cancels the previous), firing it raises WTR-107, pump-off cancels a pending timer but leaves an active WTR-107, and only `ro_tank_full` true clears it. All four are machine-scope and never touch `faults.lockouts`; raising skips an already-active code, clears skip an inactive one and use `by="hardware"`. This is deliberate double bookkeeping with `Availability`, which fails its own rows from the same inputs; only WTR-104 is in `PAYMENT_BLOCKING_FAULTS`. **Deployment rule:** the board firmware's own RO cutoff must be *longer* than `physical.ro_max_run_seconds`, so the edge always raises `WTR-107` before the board latches the pump off (the cutoff latches until a power cycle); a shorter firmware cutoff would hide the overrun from the operator.

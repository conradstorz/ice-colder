# Firmware

Scoped `CLAUDE.md`, loaded when working under `firmware/`. Moved from the root `CLAUDE.md`; project-wide rules stay there.

**`firmware/`.** `firmware/vending/` is the vending ESP32 firmware: C++ on ESP-IDF built with PlatformIO (reference board KinCony KC868-A8; spec `docs/superpowers/specs/2026-10-17-vending-esp32-firmware-design.md`, wiring and bench checklist `firmware/docs/vending-board-interface.md`). All logic lives in `lib/vendcore`, a pure C++ library behind `Clock`/`IoPort`/`Publisher` ports with no ESP-IDF or Arduino includes, so `pio test -e native` runs it on the host; `src/` holds only the ESP-IDF tasks and the KC868 drivers, and the pin map is `boards/kc868-a8.h`. The CI `firmware` job runs `pio run -e kc868-a8` and `pio test -e native`. `tests/firmware/` is an opt-in conformance suite that drives a vending board over MQTT: it is skipped unless `ICE_COLDER_BOARD_TESTS=1`, reads the broker from `ICE_COLDER_BOARD_BROKER` (`host[:port]`, default `localhost:1883`), and targets real hardware when `ICE_COLDER_BOARD_MACHINE_ID` is set, otherwise the in-process vending simulator under a fresh machine id. Tests marked `requires_sim` need the simulator to drive sensors and are skipped against hardware; that skip reason is the one legitimate board skip in `tests/skip_policy.py`, and the opt-in skip is deliberately not, because CI sets the flag and runs the suite against the simulator. `tests/firmware/test_golden_wire.py` always runs (no flag) and validates the golden JSON that `pio test -e native -f test_wire` writes into `firmware/vending/test/golden/`. Writing the suite also fixed two simulator contract gaps: a concurrent `dispense` is now rejected as busy, and `force_report` republishes capabilities and I/O. Deviations from the spec are listed in the interface doc §6 and spec §11.

**Shared platform rule.** Platform code lives in `firmware/common/` (`boardcore`, a pure C++ PlatformIO library, and `boardidf`, an ESP-IDF component, both parameterised by a `BoardIdentity`) and is never copied into a project; both firmware projects consume it, and `firmware/common` hosts its own native test env (`pio test -e native` there runs the `boardcore` ack-cache and outbound-ring tests; CI runs it too), and `boardidf::board_boot(identity, settings, after_load)` is the shared NVS/settings/console boot (after_load runs between settings load and console start: vending registers its polarity setting there, mdb installs its flash window and guard) and `boardidf::mono_ms()`/`mono_us()` the shared clock; `vendcore/ports.h` holds the one set of `using boardcore::...` declarations (there are no vendcore shim headers), and `firmware/vending`'s behaviour and goldens stay byte-identical across changes to it. `firmware/mdb/` is the MDB payment board (ESP32-S3-DevKitC-1; spec `docs/superpowers/specs/2026-10-18-mdb-board-firmware-design.md`, carrier board, provisioning and bench checklist `firmware/docs/mdb-board-interface.md`): `lib/mdbcore` is the pure-C++ MDB master behind `BusPort`/`Clock`/`IdSource`/`LogStore` ports, `src/` the bus, ledger and comms tasks, and it implements `ice_contracts.board.payment` 1.1.0. The CI `firmware` job also builds `esp32-s3-devkitc-1` and runs `pio test -e native` in `firmware/mdb` and checks `firmware/mdb/test/golden` for drift. `tests/firmware/mdb/` is the MDB conformance suite: opt-in with the same `ICE_COLDER_BOARD_*` variables, and with no `ICE_COLDER_BOARD_MACHINE_ID` it runs against the in-process MDB simulator (`ice_sims.mdb`, random customer disabled, fresh machine id), so it has no skip category of its own; `tests/firmware/mdb/test_golden_wire.py` always runs. Flash and provision either board with `scripts/flash_board.py`.
